AI - 混合推理架构：Claude 4 的“快慢思考”是怎么实现的 🧠

如果要评过去一年 AI 工程里最被低估的一个"超参"，我会把票投给 thinking budget——而不是 temperature。

这话听起来离谱。temperature 有整套调参玄学：0.3 更严谨、0.7 更有创意，无数博客教你调到小数点后两位。但真相是：在推理模型时代，temperature 对输出质量的影响，可能还不如 thinking budget 动一格。同一个模型，0 budget 和 32K budget 的行为差异，比两个不同模型还大——前者是秒回的客服，后者是能做数学证明的研究员。而大多数团队的现状是：temperature 调得飞起，thinking budget 永远留在默认值。

这就是混合推理（Hybrid Reasoning）要解决的问题：把"想多久"从模型选型里摘出来，变成一个连续可调的旋钮。

快慢思考，但只有一个大脑

"快慢思考"的说法来自卡尼曼：人类有系统 1（快、直觉）和系统 2（慢、审慎）。大模型圈借用了这个比喻，但实现走了一条更激进的路。

传统做法是两个模型各管一摊：小模型负责快，大模型负责慢。你在调用前就得决定"这个问题值不值得想"——而调用前恰恰是你最不知道问题难度的时刻。选错了，要么为简单问题付思考税，要么让难题撞上弱模型然后靠重试烧钱。

混合推理把两个系统塞进同一个模型：即时模式直接输出，扩展思考模式先输出一段 thinking 再给答案，思考预算从 0 到 32K 连续可调。关键洞察不在"快慢"，而在"连续"：推理深度不再是二选一，而是一条滑杆。简单分类用 0 预算，花 1K 抓主干，数学证明拉到 32K 展开细节——按需付费。

这带来一个反常识的结论：以后做模型选型，先别问"用哪个模型"，先问"这个问题值得多少思考 token"。很多"模型不行"的抱怨，真实原因是预算给错了。

训练上：怎么让一个模型学会"想多久"

"一个模型两种行为"听起来像把两个模型拼在一起，实际训练上有三层设计，缺一不可。

第一层：联合训练两种行为。 同一个 base 模型，同时训练"直接回答"和"先思考再回答"。这不是简单的多任务学习——模型要学会的是元判断：什么样的问题值得展开思考。这有点像训练一个学生既会抢答也会写大题，更重要的是让他看题就知道该用哪种模式。

第二层：思考过程也要被 reward。 纯结果导向的 RL 有个毛病：答案对了，但思考过程是瞎蒙的——换个问法就崩。所以 RL 阶段不只看最终答案，也给可验证的中间步骤打分。思考质量被显式优化，预算花出去才有保障。

第三层：预算条件化（budget conditioning）。 训练时随机指定 thinking budget：这次只给 1K，下次给 32K。模型被迫学会在不同预算下分配"思考精力"——预算少时抓主干、砍枝节，预算多时展开验证和反例。这就是为什么推理时你拧预算旋钮，模型真的听得懂：它在训练时就见过各种预算长什么样。

三层缺了任何一层，混合推理都会退化：没有联合训练，两种模式互相打架；没有过程监督，思考变成 token 浪费；没有预算条件化，调预算就只是一个心理安慰剂。

推理时：真正的工程红利在"路由"

模型支持调预算只是地基，真正的工程问题是：每次调用，该拧到哪一格？

答案是按难度路由（difficulty-based routing），标准做法是三级：

用户问题 → 轻量分类器（小模型，成本忽略不计）
  ├─ 简单（分类/格式化/闲聊）→ 0 budget，延迟最低
  ├─ 中等（常规代码/分析）   → 4K~8K budget，平衡
  └─ 困难（证明/复杂规划）   → 16K~32K budget，全力思考

分类器本身可能只是一个几百 token 的 prompt，成本是主调用的零头，但能把 70% 的简单请求从"思考税"里摘出来。实测中这套路由的收益经常超过"换一个更强的模型"——因为大多数生产流量本来就不需要思考。

更进一步是自动调度：连分类器都省了，模型自己判断。这一代旗舰模型陆续都走向了"自动模式"——你只管问，系统在内部决定想多久。对开发者来说，这意味着预算调优正在从"手动超参"变成"基础设施"，就像当年的数据库连接池：你不需要关心，但它一直在帮你省钱。

还有两个工程细节值得单拎出来：

思考过程的可见性是可控的。 API 允许只返回 thinking 的签名而不返回原文，下次调用可复用——长链条 Agent 场景下，这能省掉大量重复思考 token。思考不必每次都从零开始。

交错思考（interleaved thinking）：边想边调工具，而不是"想完再动"。传统 ReAct 是"想一步、调一次工具"，交错思考允许 thinking 和 tool use 穿插在同一个生成流里。对工具链长的 Agent，这减少了"想完发现缺信息、再想一轮"的浪费。

路由的代价：分类器也会犯错

按难度路由听起来很美，但它引入了一个新的故障点：分类器本身。分类错了有两种死法：

  • 把难题判成简单：0 budget 的配置去啃数学证明，结果是胡说八道——比"慢但对"糟得多，因为用户拿到的是一个自信的错误答案；
  • 把简单题判成困难：分类任务拉起 32K 思考，延迟 30 秒，账单翻 10 倍，用户只想知道"这封邮件是广告吗"。

所以路由系统需要自己的监控：抽样审计分类结果。每天抽 100 条，看"被判为简单"的请求里有没有本该深思的。分类器的准确率，就是整个路由系统的天花板。一个务实的起点：分类 prompt 里加 few-shot 示例，并且对"不确定"的请求默认走中等预算——宁可多花一点，也别把难题判简单，因为前者是成本问题，后者是正确性问题。

思考的"形状"：预算花在哪比花多少更重要

同样 8K 预算，花法不同效果天差地别。思考过程有"形状"：

  • 发散型：先列多种解法再收敛，适合开放问题；
  • 验证型：先给答案，再用剩余预算做检查和反例，适合代码生成；
  • 递进型：一步步推导，适合数学证明。

预算条件化训练让模型"听得懂"预算大小，但"形状"往往需要 prompt 引导："先给出 3 种方案再选最优"、"写完代码后用剩余预算做边界检查"。预算决定思考的"量"，prompt 决定思考的"质"。只调预算不调 prompt，等于只给了油钱没给地图。

还有一个反直觉的发现：给验证环节的预算，回报率经常高于给生成环节。让模型用 2K 生成、6K 验证（跑测试用例、找反例），比 8K 全用来生成的正确率高出一截。思考预算的分配，本身就是一门学问。

成本模型：预算就是钱

thinking token 按 output 计费——这是最贵的那档价格。一个粗糙但实用的心智模型：

任务类型 建议预算 思考/答案比 备注
分类、格式化、抽取 0 — 别为这种任务付思考税
闲聊、简单问答 0~1K ~1x 快即是好
代码生成、文档分析 4K~8K ~4x 甜点区，大部分生产任务在这里
数学证明、复杂规划 16K~32K ~10x+ 贵，但值得

注意第三列：你在为 N 份"草稿纸"付费，只为 1 份"答卷"。预算翻倍不只意味着变慢，还意味着账单接近翻倍。所以"无脑拉满预算求质量"是近年来最贵的偷懒——正确的做法是先按任务类型分级，再对每一级做 A/B：预算从 4K 加到 8K，质量提升是否配得上成本翻倍？大多数团队测完会发现，甜点比想象中低。

预算调优的实操方法

理论都懂，落地时怎么找到自己业务的"甜点"？三步：

  1. 分级采样：从生产流量里按任务类型各抽 200 条，覆盖简单/中等/困难；
  2. 网格扫描：对每级跑 0 / 1K / 4K / 8K / 16K 五档预算，记录质量分（人工抽查或 LLM-as-judge）和成本；
  3. 画边际曲线：横轴预算，纵轴质量。曲线变平的那个拐点，就是你的甜点——超过拐点的每一分钱，都是纯浪费。

注意两个细节：扫描要在生产分布上做，别用测试集——测试集的难度分布和线上往往差一个量级；模型版本升级后重扫一次，新一代模型的拐点通常更靠左（更少的思考达到同样的质量）。

落地清单

  1. 给预算建档：把核心调用按任务类型列出来，每个标一个初始 budget（从上表起步），而不是全用默认；
  2. 延迟分级：用户-facing 的交互用即时/低预算（先快再说），后台批处理任务用高预算（慢慢想）；
  3. 先路由，再换模型：账单超了先上难度路由，70% 的流量可能根本不需要思考模型；
  4. 定期复查预算：模型升级后重测甜点——新一代模型用更少的思考 token 达到同样质量，预算是要跟着下调的。

混合推理真正的遗产，不是某一个模型，而是一个观念的切换："选模型"变成了"分预算"。以后的 AI 工程讨论可能不再是"你用过哪些模型"，而是"你的思考预算是怎么分配的"——能答好这道题的人，才是真的在生产环境里写过代码的人。

AI - GPT-5 的“一体化”：路由模型是怎么选模型的 🧭

GPT-5 把"选模型"这个动作删了：不再有"GPT-4o 还是 o3"的选择题，只剩一个入口，系统内部自动决定用快模型还是深度思考。这篇拆解这个"路由器"到底是怎么做的，以及为什么"一个入口，智能分发"会是所有 AI 应用的终点形态。

GPT-5 发布那周，所有人都在讨论跑分涨了多少。但跑分是会过时的——真正留下来的是一个看似不起眼的产品细节：模型选择器被删了。

这不是 UI 改版。这是 OpenAI 第一次公开承认："选模型"这个负担，不该由用户来扛。而扛下它的东西，叫路由器（router）。

删掉选择器，为什么是大事

先看用户侧的变化：

之前：
  写代码 → 纠结选 o3（慢但强）
  闲聊   → 选 4o（快但弱）
  选错了 → 要么等半天，要么答案拉胯

之后：
  只有一个输入框，系统自己决定"快答"还是"深想"

这解决的是一个经典的产品困境：选择悖论。模型越多（旗舰、轻量、推理、多模态……），用户选对的概率越低，选错的挫败感越强。把 5 个模型摆在用户面前，本质上是把内部的工程复杂度转嫁给了用户。

更深一层，这是商业模式的位移：从"卖模型"到"卖能力"。用户买的不再是"某个模型的调用次数"，而是"问题被解决"。中间那层"哪个模型来解"，成了供应商的内部事务——就像你买云服务器，不关心它被调度到了哪台物理机。

路由器是怎么做的：三种实现

1. 规则路由：最糙，但曾经够用

关键词/正则匹配："证明"→推理模型，"翻译一下"→快模型。

if any(kw in query for kw in ["证明", "推导", "prove"]):
    route_to("reasoning-model")
elif len(query) < 20:
    route_to("fast-model")

优点是零延迟、完全可解释；缺点是脆弱——"证明我没拿你东西"也会被送去深度思考。这是前两年的过渡方案，现在只适合做兜底。

2. 小模型分类器：当前主流

用一个轻量模型先判断查询的类型和难度，再分发给对应的大模型：

用户问题 → 分类器（约 50ms，可忽略）
  ├─ 闲聊/简单问答 → 快模型（便宜一个数量级，快数倍）
  ├─ 中等难度       → 标准模型
  └─ 数学/代码/复杂推理 → 推理模型（放开思考预算）

这里有个精妙的自举：分类器的训练数据，是用最强模型标注出来的。用旗舰模型给海量 query 打"难度分"，再蒸馏出一个小分类器——大力出奇迹，再用小力省钱。

但分类器路由有个天然上限：它只能做"请求级"路由。一个问题进去、选定模型，就一条道走到黑。如果对话中途难度突变（"顺便帮我证明一下这个结论"），分类器无能为力。

3. 模型内路由：GPT-5 的方向

单个大模型内部，按需分配计算量——简单问题算几层就 early exit，难题全量计算。这已经不是"选模型"，而是**"选算力"**：

  • 按 token 分配：每个 token 的生成难度不同，简单的少算、难的多算（自适应计算）；
  • MoE 的亲戚：MoE 是按 token 选专家，模型内路由是按难度选"思考深度"，思想同源；
  • 与混合推理合流："快思考/慢思考"不再是两个模型，而是一个模型的两种工作模式。

这是"路由"概念的终极形态：路由层从系统架构，下沉到了模型架构。以后可能没有"路由器"这个独立组件了，因为模型自己就是路由器。

不过短期内，2 和 3 会长期共存：分类器管"选哪个模型"，模型内路由管"每个模型内部怎么省算力"。

四个工程难点，一个比一个贵

难点一：误判的代价不对称

这是路由调参的第一性原理：

误判方向 后果
难题判成简单题（under-thinking） 答案错——用户直接流失
简单题判成难题（over-thinking） 多花点钱、多等几秒——用户基本无感

把难题判错的代价，比把简单题判错高一个数量级。 所以路由器的阈值永远偏向"宁可多想"：宁可让 30% 的简单问题走推理模型，也不让 1% 的难题被敷衍。这也解释了为什么一体化系统早期总被吐槽"变慢了"——保守策略下，大量本可以快答的问题被送去深想了。

工程上的解法是分级阈值 + 事后升级：先按宽松阈值路由，如果快模型的回答置信度低（self-evaluation），再升级到强模型重做。用一次廉价尝试，换一份保险。

难点二：冷启动

新用户没有历史，第一次路由只能靠纯文本判断——准确率最低的时候，恰恰是用户形成第一印象的时候。

务实的做法：新用户默认保守（偏向强模型），同时用前 10 次交互快速校准分类器。冷启动不是技术问题，是体验问题：别在用户最在乎的时候掉链子。

难点三：可解释性

用户问"为什么这次这么慢"，客服得能回答；企业客户做审计，得知道"我的请求到底走了哪个模型、花了多少钱"。

OpenAI 在 API 里暴露了实际使用的 reasoning_effort，算是一种交代。但这只是开始——成熟的路由系统需要完整的路由日志：每个请求走了哪条分支、分类器打了多少分、为什么没走另一条。没有这个，路由就是黑盒，黑盒进不了企业。

难点四：评估归因模糊了

"某一体化模型在 benchmark 得分 90"——是哪个子模型得的？ 一体化让评测的归因变得模糊，甚至留出了作弊空间：理论上，供应商可以把"疑似评测题"全部路由到最强的内部模型，刷出漂亮的数字，而日常用户走的却是便宜分支。

对策是按难度分层评测：别只看总分，看"简单题走快模型的答对率"和"难题走强模型的答对率"两条曲线。做 AI 选型的团队，评测报告里必须有这一页。

难点五：路由本身的开销

路由器不是免费的。分类器一次推理 50-200ms，对"闲聊"这种 300ms 就能答完的请求，路由开销占比超过 30%——为了省钱花的钱，不能超过省下的钱。

工程上有三层优化：

  1. 分类器和首 token 并行：不等分类结果，先用默认模型开始生成，分类结果出来后再决定是否切换（投机式路由）；
  2. 缓存路由决策：同一用户的相似问题，路由结果大概率相同——embedding 相似度超过阈值直接复用上次决策；
  3. 级联路由：先用超轻量规则做粗分（明显闲聊直接走快模型），只有模糊地带才上分类器。把 80% 的请求挡在第一层，分类器只处理 20% 的疑难杂症。

还有一个隐形开销：路由器的维护成本。新模型上线，分类器的"难度标尺"要重标；用户行为漂移，分类器要重训。路由器本身是一个需要持续运营的 ML 系统，不是写一次就完事的 if-else。很多团队第一版路由上线时效果惊艳，半年后悄悄腐化——就是因为没人维护分类器。

给开发者的五条建议

1. 别再让用户选模型。 你的 AI 产品也该做路由——意图分类 + 按难度分发，好过把 5 个模型摆在用户面前让用户做阅读理解。路由最好的 UI 形态，就是"没有 UI"。

一个最小可用的路由架构长这样：

def handle(query, session):
    # 1. 会话级 sticky：同一会话优先保持上次路由，避免人格跳变
    if session.last_route and not difficulty_shifted(query, session):
        return dispatch(session.last_route, query)
    # 2. 级联分类：规则粗分 → 小模型细分
    route = rule_filter(query) or classifier.predict(query)
    # 3. 置信度兜底：分不清就升级，宁可多想
    if route.confidence < 0.7:
        route = escalate(route)
    log_route(query, route)  # 4. 路由日志：可审计是底线
    return dispatch(route, query)

**1. 别再让用户选模型。** 你的 AI 产品也该做路由——意图分类 + 按难度分发，好过把 5 个模型摆在用户面前让用户做阅读理解。路由最好的 UI 形态，就是"没有 UI"。

**2. 成本优化空间是真实的。** 实测中，约 70-80% 的查询用便宜模型就能处理好，只有 20-30% 需要旗舰模型。账单直接砍半，比任何"换便宜模型"的谈判都管用。思考模型的"思考税"之前专门算过一笔账，路由正是降本的第一杠杆。

**3. 先解决多轮一致性。** 同一会话里切模型，会导致风格跳变、上下文理解断裂。工程上用 **sticky routing**：会话一旦路由到某模型，后续轮次优先保持，难度变化时再整体升级。别让用户感觉"突然换了个人格"。

**4. 路由是权力，要有制衡。** 暗黑模式预警：供应商完全可以把免费用户悄悄路由到便宜模型、把高价值问题优先送强模型——用户无从察觉。作为开发者，给自己的路由系统加三条红线：路由日志可审计、用户可手动指定模型（高级选项）、定期公布路由分布。**路由即权力，权力需要被看见。**

**5. 给路由建观测。** 四个指标每周看一次：路由分布（各分支占比是否符合预期的 80/20）、升级率（快模型→强模型的比例，超过 15% 说明分类器太激进）、P99 延迟分层（路由开销有没有吃掉省下的时间）、人工抽样误判率。**没有观测的路由，半年后一定腐化。**

## 一体化之后，拼的是路由

GPT-5 的"一体化"会被记住，不是因为它更强，而是因为它第一个把牌摊在了桌上：**用户侧只剩一个输入框，复杂度全部沉到路由层**。CDN 按线路路由请求，K8s 按负载调度容器，云按需分配算力——AI 按难度分配智能，是同一条路的下一站。

模型会继续变多、变强、变便宜，但"选模型"这个动作不会回来了。路由层正在成为 AI 应用的水电煤：看不见，但缺了它，一切都转不动。先把它吃透的团队，会先拿到成本和体验的双重红利——这不是预测，是已经发生的账单。

工程化 - 疑难 bug：WebSocket 百万连接的心跳与内存 🔌

凌晨 3 点 17 分，PagerDuty 把我震醒：推送服务的内存曲线像爬楼梯一样，每周涨 10GB，今晚终于撞上了 OOM 的红线，K8s 开始杀进程。

我爬起来看监控：连接数 100 万，CPU 40%，QPS 平稳——经典的"什么都没满，但服务就是不行"。重启服务，内存掉回基线，一切正常。一周后，曲线又爬回来了。

重启能好，说明问题不在流量，在状态堆积。而 100 万长连接的服务，状态堆积只有几个嫌疑人。这篇复盘我们抓到的三个。

真凶一：TCP 半开连接

先看一张图：

客户端：App 被系统杀掉 / 用户从 WiFi 切到 4G / 电梯里没信号
服务端：？？？——服务端完全不知道，连接还显示 ESTABLISHED

TCP 是个"沉默的协议"：只要没人主动说再见，连接就一直算活着。TCP 自带的 keepalive？默认 2 小时才发第一个探测包——2 小时内，服务端以为 100 万连接都活着，其实可能一半已经死了。

每个"死连接"都在悄悄吃内存：socket fd、内核收发缓冲、应用层的用户会话对象、订阅关系。单个看很小，100 万连接里混进 30 万个死的，内存曲线就开始爬楼梯了。这就是"假在线"：客户端看着连着，服务端看着连着，其实对端早就没了。

还有一个"慢性"的半开来源：NAT 超时。移动网络的 NAT 会话表项几分钟不活动就回收，公网 IP 变了，服务端的连接还在——客户端重连用的是新五元组，老连接在服务端继续"装活"。这就是为什么移动端 App 的假在线比 PC 严重得多：NAT 让"沉默的断开"成了常态。

修复：应用层心跳

别指望 TCP keepalive，自己在应用层做心跳：

// 服务端：30 秒 ping 一次，60 秒没回 pong 就掐
ws.on('pong', () => { conn.isAlive = true; });
const interval = setInterval(() => {
  wss.clients.forEach((ws) => {
    if (ws.isAlive === false) return ws.terminate();  // 掐掉假活的
    ws.isAlive = false;
    ws.ping();
  });
}, 30000);

两个细节决定成败：

第一，用 terminate()，不用 close()。 close() 要走 WebSocket 关闭握手——对端都死了，握手包永远等不到，连接继续半死不活地占着资源。terminate() 直接销毁 socket，不废话。长连接做得好不好，看的不是"连上"，是"断得干净"。

第二，心跳间隔是业务参数，不是技术参数。 30 秒/60 秒是 IM 的常见值；如果是 IoT 设备上报，为了省电可能 5 分钟一次。间隔越短，假在线发现越快，但心跳开销越大——这是成本和实时性的 trade-off，得按业务拍板。

真凶二：心跳风暴

心跳加上线，内存曲线不涨了。但一周后，CPU 告警了——平时 40%，心跳时刻飙到 90%。

算一笔账就明白了：

100 万连接 × 每 30 秒一次 ping = 每秒 3.3 万次 ping
每次 ping：定时器回调 + 网络 IO + 状态更新

更要命的是对齐：所有连接同一时刻建连（比如服务重启后客户端批量重连），心跳也同一时刻触发——3.3 万次 ping 变成同一秒内的 100 万次。这就是心跳风暴：治好了假在线，心跳本身成了新的病。

修复：打散 + 退避

// 1. 分桶：把连接打散到 60 个桶，每秒只 ping 一个桶
const buckets = Array.from({length: 60}, () => new Set());
// 新连接随机进桶，心跳按桶轮询

// 2. 退避：移动端在后台时，心跳间隔从 30s 放到 5min
//    反正后台也收不到推送，不如省电省服务器
if (client.isBackground) interval = 300000;

分桶把"每秒 3.3 万次"变成"均匀分布的每秒 1.6 万次"，退避把移动端后台连接的心跳量砍掉 90%。心跳的本质是"抽查"，不是"点名"——抽查就要随机、分散，别搞成大阅兵。

真凶三：内存账本

前两个修完，内存曲线终于平了。但我们又做了一次容量复盘，发现之前的估算全是拍脑袋。这次认真算了一次账：

单连接内存 ≈
  socket fd + 内核缓冲：                 ~20KB
  应用层会话对象（用户信息、订阅关系）：   ~10KB
  读缓冲（TCP 窗口、ws 帧缓冲）：          ~50KB
─────────────────────────────────────────
  合计约 80KB/连接
  100 万连接 ≈ 80GB

80GB——单机扛不住是数学决定的，不是优化能解决的。所以百万连接的第一步永远是"先算账，再架构"：

  1. fd 上限：默认 1024，百万连接要调到百万级（ulimit -n），还要调内核的 net.core.somaxconn、tcp_max_syn_backlog；
  2. epoll：Node、Go、Java NIO 都是 epoll 那套，单线程能 hold 住百万 fd——瓶颈不在 IO 模型，在内存；
  3. 分片：按 userId 一致性哈希打到 N 台机器，每台 20-30 万连接，留足水位，别压到极限。

调内核参数时有个经验：net.ipv4.tcp_mem 控制 TCP 内存总量，net.core.rmem_max/wmem_max 控制单个 socket 缓冲上限。百万连接下，这些值要按"连接数 × 单连接预算"反推，而不是用默认值。默认值是为 1 万连接设计的，不是为 100 万。

还有一个隐性内存杀手：读缓冲的动态膨胀。TCP 接收缓冲会按需自动调大，一个"慢消费者"客户端能把服务端的发送缓冲撑到几 MB。解法是设 SO_RCVBUF/SO_SNDBUF 上限，或者在应用层做背压（backpressure）——消费慢的连接，降级甚至踢掉，别让它拖垮整台机器。长连接服务里，最慢的那个客户端决定你的内存水位。

分桶把"每秒 3.3 万次"变成"均匀分布的每秒 1.6 万次"，退避把移动端后台连接的心跳量砍掉 90%。心跳的本质是"抽查"，不是"点名"——抽查就要随机、分散，别搞成大阅兵。

实现上还有个细节：别给每个连接单独 setInterval。100 万个定时器，Node 的 timer 堆直接爆炸。正确做法是全文示例里那样——一个全局定时器轮询所有连接，或者按桶做层级时间轮（timing wheel）。定时器本身，也是要"打散"的资源。

网关层：把"连接"和"业务"拆开

百万连接的架构里，有个经典分层：

客户端 → 接入网关（只管连接：握手、心跳、编解码） → 业务服务（只管逻辑）
                                                   ↓
                                              Redis/消息队列

网关层是无状态的，只做三件事：维持连接、做心跳、转发消息。业务逻辑全在后面的服务里，通过消息队列通信。

这样拆的好处：网关可以按连接数水平扩展，业务按 QPS 扩展——两种资源的 scaling 曲线不一样，拆开才能各自优化。坏处是多了一跳延迟，IM 场景下通常多 1-2ms，可以接受。

还有一个配套设计：粘性会话。同一用户的连接固定打到同一台网关（按 userId 哈希），这样"单聊消息"不用跨机器广播。代价是扩缩容时要做连接迁移——新机器上线，老连接逐步搬过去，别一次性全断。扩容时最忌讳的，就是"为了扩容，先把所有连接掐了"。

容易漏的第四个坑：离线消息积压

这个坑不在连接本身，在重连的那一刻。用户离线 3 天，重连瞬间，服务端把离线期间的消息全推过去——10 万条消息砸进一个 WebSocket，App 直接卡死。

铁律：WebSocket 只做"实时"，不做"历史"。

// 离线消息只推最近 100 条 + 未读数，历史走 HTTP 分页拉
const offline = await redis.lrange(`offline:${uid}`, 0, 99);
ws.send(JSON.stringify({ type: 'sync', messages: offline, unread: total }));

重连时先给一个轻量的 sync 包（最近消息 + 未读数），用户往上翻历史时再走 HTTP 分页拉。实时通道保持轻，历史走批量通道——职责分开，两个都快。把历史塞进实时通道，是"图省事"变成"找麻烦"的典型。

第五个坑：重连风暴

前面说的都是"稳态"，还有一个"瞬态"杀手：服务端重启后，100 万客户端同时重连。

服务恢复 → 100 万个 TCP 握手同时打过来
        → 100 万次鉴权（查 DB/Redis）
        → 100 万次离线消息同步

这就是惊群（thundering herd）。解法是退避 + 抖动：客户端重连时 sleep 一个随机时间（比如 0-30 秒），把 100 万次握手摊平到 30 秒里。服务端侧，鉴权加缓存，离线消息走前面说的轻量 sync。

记住：长连接的灾难，一半发生在"断"，一半发生在"重连"。只设计了心跳，没设计重连退避，等于只修了一半。开篇那个凌晨重启"好了"的服务，如果第二天所有客户端同时回连，没有退避的话，迎接你的就是第二次告警。

监控清单：这 5 个指标必须看

  1. 连接数 vs 内存：两条曲线的比值应该恒定，比值爬坡 = 有泄漏；
  2. 心跳超时率：突然升高 = 网络抖动或客户端批量死亡；
  3. 单连接内存 P99：平均数会掩盖"慢消费者"，看 P99；
  4. 重连率：重连率飙升 = 服务端在"被动"踢人，查心跳配置；
  5. 消息延迟 P99：从发送到接收的端到端延迟，长连接的核心 SLA。

这 5 个指标进 Prometheus + 告警，比事后查日志有用 10 倍。开篇那个凌晨 3 点的事故，如果早有"连接数/内存比值"告警，第一次爬坡时就能发现，不用等到 OOM。监控不是"出事了看"，是"没出事时就盯着比值"。

凌晨 3 点 17 分的那个告警，最后是这样收尾的：心跳加上了，风暴打散了，内存账本算清了，曲线再也没爬过楼梯。

但这件事给我留下的真正教训，不在上面任何一节里。复盘会上，有人问："为什么测试环境从来没复现过？"答案很扎心：测试环境只有 1 万连接，而半开连接、心跳风暴、缓冲膨胀，全是"量变引起质变"的问题——1 万连接时，它们连噪音都算不上；100 万连接时，每个都是杀手。

所以长连接的压测，只有一个标准：用生产级的连接数压。拿 1 万连接的压测报告去论证 100 万连接的架构，等于拿游泳池的成绩去报名横渡长江。

下次凌晨 3 点再被叫醒，我希望是因为别的原因。

AI - MoE 专家并行：当"通信"成为第一瓶颈

同样的 GPU，同样的算力，两套万亿 MoE 训练集群，吞吐差一倍。差的不在芯片，在网线——30% 的训练时间，H100 不在计算，在等数据。

MoE 专家并行：当"通信"成为第一瓶颈

一个典型的万亿 MoE 训练配置：384 个专家分布在 64 张 GPU 上，每个 token 路由到 top-8 专家，batch 4M tokens，hidden dim 8192，FP8 精度。

每步训练的通信量：

dispatch（发出去）: 4M × 8192 × 1 byte = 32GB
combine（收回来）:  32GB
合计 ≈ 65GB / step

NVLink 900GB/s，看起来 65GB 是洒洒水。但魔鬼在细节里：all-to-all 不是一次 65GB 的大传输，而是成千上万次小消息的高频收发——建连、同步、协议开销摊下来，实际带宽利用率经常只有 30%。

更麻烦的是负载不均：某个专家突然成"网红"，一半 token 涌向它所在的 GPU，这张卡就成 straggler——通信耗时取决于最慢的那张卡，不是平均速度。2026 年万亿模型的竞争，表面是参数，里子是互联。

一、拓扑感知：让"好朋友"住一起

朴素的专家放置是随机撒：384 个专家均匀分到 64 张卡，每个 token 的 8 个目标专家大概率散落 5 台机器，跨机 InfiniBand（400GB/s）拉满。

优化思路：分析历史路由数据，找出"经常一起被选中"的专家组合，放同一台机器。

朴素：token → 8 个专家散落 5 台机器 → 跨机通信 × 5
优化：token → 8 个专家集中 1-2 台机器 → 机内 NVLink 为主

机内 NVLink 900GB/s 对跨机 IB 400GB/s，带宽差一倍，延迟差一个数量级。这一步，通信时间直接砍半。

代价：放置策略要跟着路由分布走——训练初期路由剧烈震荡，昨天的"好朋友"今天可能形同陌路。拓扑感知不是一劳永逸的配置，是需要定期重算的动态策略。

二、重叠与量化：把通信"藏"起来、"压"小

通信计算重叠是大模型训练最经典的技巧，在 MoE 上收益最大：

串行：[计算] → [通信] → [计算] → [通信]   （通信时间纯浪费）
重叠：把 token 切成 micro-batch，
      前一批 all-to-all 传输时，后一批矩阵乘法已经在跑

GPU 是"双车道"——计算单元和 NCCL 通信引擎可同时工作。通信时间被计算时间掩盖，用户感知到的额外开销趋近于零。 前提是计算量够厚，能盖住通信；盖不住，就先回第一招把总量降下来。

混合精度通信则是不对称的精明：

dispatch（分发 token 给专家）: FP8 足够
  → 路由的是"输入"，精度损失影响小
combine（专家结果加权求和）: 需要 BF16
  → 大量数值累加，低精度引入系统性偏差

不是一刀切全量化，而是逐个环节分析精度敏感度，带宽需求再降 40%。注意量化本身有 kernel 开销，超过通信时间的 10% 就得不偿失。

三、动态放置：热专家多开分店

训练初期路由震荡，"网红专家"导致 straggler；后期分布稳定。静态放置在初期频繁翻车。

解法是动态迁移，DeepSeek V3 技术报告里提过类似思路：

  • 热专家复制：负载最高的专家复制到多张卡，分流请求——给网红店多开分店；
  • 冷专家合并：长期无人问津的专家并到同一张卡，腾位置。

本质是把"负载均衡"从通信层下沉到放置层：与其让 token 跋山涉水找专家，不如让热门专家靠近 token。 代价是多副本的梯度同步开销，但比起 straggler 拖慢全局，通常划算。

还有个更隐蔽的维度：路由均衡本身。auxiliary loss 惩罚"某些专家被过度选中"，有效，但扭曲了路由的"真实偏好"——模型想把 token 发给最擅长的专家，aux loss 硬赶去别的专家，等于拿模型质量换通信效率。这是不可能三角：模型质量、通信效率、实现复杂度，最多取其二。

四、推理侧：更难的"即时配送"，和釜底抽薪的三招

训练是"批量快递"，推理是"即时配送"：batch 小（通信占比反而更高）、延迟敏感、不能攒波次。解法是专家亲和性调度——同一用户的连续请求路由到同一组 GPU。用户请求主题连贯，激活的专家集合高度重合，"老熟人"固定在同一组卡上，跨机通信自然少。vLLM 和 SGLang 都在往这个方向做。

但所有优化都在"把通信做快"，还有一派问：能不能少通信？

  • 路由变稀疏：top-8 降到 top-2，通信量砍 75%。代价是容量利用率下降——质量换效率，推理场景值得。
  • 共享专家：设几个常驻专家，所有 token 都过，不需要路由、不需要 all-to-all。DeepSeek V3 用过这招——一部分计算"免通信"，总量自然下来。
  • 专家合并剪枝：训练后期把功能重叠的专家合并。384 个里可能 50 个冗余——拓扑更稀疏，模型还更小。

这三招的共同点：从架构层面减少通信需求，而不是在通信层面优化。

结语

模型参数每 18 个月翻几倍，互联带宽的增长慢得多。当通信占比从 30% 爬向 50%、70%，上面的招式榨干之后，下一个突破口要么是下一代互联（光互联、共封装光学），要么是抛弃 all-to-all 的新路由范式。

可以确定的是：你的模型能做多大，不取决于买了多少 GPU，取决于 token 能跑多快。 未来几年，系统工程师在 MoE 项目里的话语权只会越来越大——懂模型的人很多，同时懂模型和互联的人很少，而万亿模型的胜负手，恰恰藏在这两者的交叉点上。

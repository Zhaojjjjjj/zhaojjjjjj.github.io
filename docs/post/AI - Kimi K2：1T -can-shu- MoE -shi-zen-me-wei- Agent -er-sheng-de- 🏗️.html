AI - Kimi K2：1T 参数 MoE 是怎么为 Agent 而生的 🏗️

关于 Kimi K2，最反常识的一个事实是：它号称 1 万亿参数，但每次推理真正参与计算的，只有 3% 左右。

先别急着说"虚假宣传"。这 3% 恰恰是它最聪明的设计——一个万亿参数的模型，核心竞争力不是"大"，而是"学会了偷懒"。

1T 是怎么"装"下的

MoE 的账其实很直白：

总参数：1T（1000B），384 个专家
每次推理：路由选 8 个专家，约 32B 参数参与计算

存储要按 1T 准备（多卡、量化、专家并行），但计算量只相当于一个 32B 的 dense 模型。这就是 MoE 的核心套利：用存储换能力，用稀疏换速度。

对比一下 dense 路线的 1T 会是什么下场：每生成一个 token，都要把 1T 参数从 HBM 里搬出来过一遍。光是"搬参数"这一步，延迟和能耗就扛不住；KV Cache 还要再翻几倍。dense 的 1T 在推理侧是个死胡同，MoE 让"大"和"快"第一次不矛盾。

但这里有个容易被忽略的细节：稀疏不是免费的。384 个专家放在多卡上，token 要在 GPU 之间 dispatch（分发）再 combine（汇总），all-to-all 通信在训练时能吃掉可观的时间占比。推理时如果专家分布在多卡，跨卡通信同样会吃掉延迟。所以 MoE 部署的第一性问题永远是：专家怎么放，放几卡。回答不好这个问题，1T 的纸面参数就是摆设。

路由：MoE 真正的大脑

MoE 的灵魂是门控网络（gating network）。每个 token 进来，门控网络打分，选出 top-8 的专家：

token → gating(x) → scores[384] → top-8 → 加权求和

这里藏着 MoE 训练最难的一课：路由会偷懒。如果不加约束，门控网络很快发现"只用前 10 个专家也能把 loss 降下去"，剩下 374 个专家变成死参数——你训了 1T，实际只用了 100B，存储的钱白花了。

解法是 aux loss（辅助损失），强制专家的负载均衡：用得多的专家被惩罚，用得少的被鼓励。但 aux loss 的权重是门艺术——给大了，模型为了"均衡"牺牲主任务；给小了，路由继续偷懒。训 1T MoE 的团队，一半时间都在跟这个系数较劲。

还有一个更深的设计分歧：token-choice 还是 expert-choice？token-choice（每个 token 自己选专家）简单直观，但负载天然不均；expert-choice（每个专家挑自己擅长的 token）均衡性好，但实现复杂，还可能丢 token。主流开源 MoE 目前走的都是 token-choice + aux loss——简单、可扩展、够用，工程上永远是先选能落地的。

顺带说个推理时的细节：路由本身也有成本。每个 token 都要过一遍门控网络（384 维打分），这部分计算省不掉。不过和 32B 的专家计算比起来，门控的开销可以忽略——MoE 的账，永远只看大头。

为什么 MoE 偏偏适合 Agent

这是 K2 最值得深挖的一点。Agent 任务有两个特点，恰好撞上 MoE 的长处：

第一，任务多样性极高。 一个 Agent 流程里，写代码、读文档、调工具、做规划——子任务的分布极其发散。dense 模型是"一个大脑干所有活"，MoE 是"专家会诊"：代码 token 路由到代码专家，工具调用的 token 路由到擅长结构化输出的专家。专家的分工，天然对应 Agent 的多任务本质。 这不是巧合，是架构和任务分布的同构。

第二，长程推理的成本。 Agent 动不动就是几十轮工具调用，上下文动辄上百 K。K2 给了 256K 上下文——注意这个组合：长上下文 × 稀疏计算。dense 模型里，长上下文意味着每个 token 都要过全部参数，成本随长度线性爆炸；MoE 里，每 token 只激活 32B，长程任务的成本第一次变得可控。这是架构层面的匹配，不是调参调出来的。

但架构只是上半场。K2 真正为 Agent 下注的地方在数据：训练里加了大量 agentic 数据——工具调用轨迹、多步任务的完整 rollouts、带环境反馈的交互序列。模型不是"学会了文本"，而是"学会了干活"。这解释了为什么 K2 的 Agent benchmark 成绩能打：能力来自数据的分布，不只来自参数的规模。架构决定上限，数据决定能不能摸到上限。

推理侧的经济学

开源 1T MoE，大家最关心的问题从来不是"强不强"，而是"跑不跑得起"。算三笔账：

第一笔：KV Cache。 Cache 的大小只和激活的参数、层数、上下文长度相关——MoE 的 Cache 成本按 32B 算，不是按 1T 算。这是 MoE 推理友好的隐藏红利，很多人算账时漏掉了这一项。

第二笔：专家放置。 384 个专家不可能全放 HBM。常见做法：热专家放 GPU，冷专家 offload 到 CPU 或内存，按需加载。有意思的是，Agent 场景下专家的冷热分布恰好对应任务分布——工具调用类的专家可能是热的，闲聊类的专家可能是冷的。** workload 的形状，决定了部署的形状。**

第三笔：量化。 1T 的 FP16 是 2TB，int8/int4 量化后进到几百 GB，多卡 H100 级别的机器能跑。这就是为什么 K2 开源（modified MIT）有意义：第一次，普通团队能私有化部署一个 Agent 能力顶级的模型——数据不出内网，微调、蒸馏都自己说了算。

还有一个被低估的用法：只微调被激活的专家。全量微调 1T 不现实，但 LoRA 打在高频激活的专家上，参数量可控，效果集中。这是 MoE + LoRA 的化学反应——稀疏架构和稀疏微调，天生一对。

agentic 数据具体长什么样

前面说 K2 在数据层面为 Agent 优化，具体长什么样？不是"问答对"，而是完整的"干活轨迹"：

用户：帮我把这个报错修了
Agent：[读日志] → [定位文件] → [改代码] → [跑测试] → 失败
      → [读测试输出] → [再改] → [跑测试] → 通过

每一步的工具调用、每一次的环境反馈、每一次的试错，都是训练信号。模型学到的不是"正确的答案"，而是"正确的工作方式"。这就是为什么 K2 在 Agent benchmark 上能打——它见过"干活"的样子，而不只是"说话"的样子。

这类数据的获取成本极高：要跑真实环境、要采多步轨迹、要过滤失败案例。这是 K2 的隐性护城河，也是开源社区最难复现的部分——权重可以下载，产生权重的"干活数据"下不下来。开源的从来不只是权重，还有权重背后的数据工程，只是后者没法开源。

部署实战：MoE 的并行策略

把 1T MoE 跑起来，并行策略选错，性能直接腰斩。三种并行各管一段：

张量并行（TP）：把单个专家切分到多卡。适合"专家放不进单卡"的场景，但通信密集——每次前向都要 all-reduce。对 MoE 来说，TP 通常只用在"专家本身太大"时；K2 这种激活量 32B 级别的模型，单专家不大，TP 不是主角。

专家并行（EP）：一个 GPU 放几个专家，token 按路由结果分发。这是 MoE 的主场。EP 的规模直接决定你能放下多少专家：384 个专家，EP=8，每卡 48 个专家。EP 的代价是 all-to-all 通信——token 要在卡之间"快递"两次（dispatch + combine）。

流水线并行（PP）：把层切分到多卡。通信量小，但有 pipeline bubble。

实战中的组合通常是 EP + TP 混合：EP 解决"专家太多"，TP 解决"单专家太大"。vLLM 和 SGLang 对 MoE 都做了专门优化——比如 expert parallelism 的 fused kernel、按专家粒度的量化。选推理框架时，先看它对 MoE 的支持成熟度，再看别的。

还有一个量化细节：MoE 量化不能"一刀切"。不同专家的权重分布差异很大，统一的量化 scale 会让某些专家精度崩掉。逐专家（per-expert）量化是必须的——这是 dense 模型量化经验里没有的一课。

Dense vs MoE：一张对照表

维度 Dense 1T（假设） MoE 1T（K2）
推理计算量 1T 全激活 ~32B 激活
KV Cache 按 1T 计 按 32B 计
显存占用 参数全放 HBM 专家可 offload
训练通信 TP/PP 为主 EP 的 all-to-all 是大头
稳定性 相对成熟 loss spike 更频繁
任务适配 通用 多任务/长程任务占优

这张表说明一个事：MoE 不是 dense 的"省钱版"，是另一个物种。它的优势项（推理成本、任务分工）和劣势项（训练复杂度、通信）都来自"稀疏"这个第一性原理。选架构之前，先问自己的 workload 是"单一任务大力出奇迹"，还是"多任务长程作战"——答案不同，架构就该不同。

训练侧的地狱

训 1T MoE 有三道坎。前面提了负载均衡和通信，第三道是稳定性。MoE 的 loss spike 比 dense 频繁得多——某个专家的梯度突然爆炸，整个训练就崩了。业界的解法是更激进的 gradient clipping、更长的 warmup，以及对路由权重的特殊处理。K2 技术报告里提到的 MuonClip 这类优化器改进，本质上都在回答同一个问题：怎么让 384 个专家的训练不互相拖后腿。

这三道坎有一个共同点：它们都是"规模"带来的新问题，不是"模型"本身的问题。dense 时代的老经验（调 lr、加数据）在这里不够用了，MoE 把大模型训练从"炼丹"变成了"系统工程"。

一个开放的问题

K2 证明了一件事：Agent 时代，架构比参数量重要。1T 的噱头之下，真正的遗产是"稀疏计算 × agentic 数据"这套组合。

但问题也随之而来：专家的数量继续涨到 1024、2048，收益还跟得上吗？还是说，未来的方向是更细粒度的"微专家"——每个专家只会一件事，路由变成真正的任务调度器？MoE 的稀疏度，极限到底在哪？

这个问题现在没有答案，但它决定了下一代 Agent 模型的长相。而 K2 的价值，就是把这个问题从论文里拽到了现实中，让所有人都能动手验证。

顺着这个问题再想一步：如果未来的模型是"几万个微专家"，训练范式也会变——不再是"训一个大模型"，而是"训一个专家市场"：新任务来了就加几个专家，老专家不动。这和今天"一个模型打天下"的思路完全不同。K2 可能是这个转变的起点，也可能只是中间站。时间会给出答案，但在那之前，动手把 1T 跑起来的人，已经赢了。

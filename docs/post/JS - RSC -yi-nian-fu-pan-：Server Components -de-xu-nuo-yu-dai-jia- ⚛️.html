JS - RSC 一年复盘：Server Components 的许诺与代价 ⚛️

RSC（React Server Components）落地一年多了。我最近问了五个用 Next.js App Router 的团队：三个说"真香"，两个说"正在迁回去"。同一个技术，评价两极——分歧到底在哪？

当初许诺了什么

RSC 出来时，官方给了三个许诺。我们一个个看兑现了几成。

许诺一：零 bundle 的组件

服务端组件不进客户端 bundle。markdown 渲染、代码高亮、日期格式化这类重库，直接在服务端跑：

// 服务端组件：highlight.js 只在服务端存在
import hljs from 'highlight.js'; // 200KB，不进 bundle
export default async function CodeBlock({ src }) {
  const html = hljs.highlight(src).value;
  return <pre dangerouslySetInnerHTML={{ __html: html }} />;
}

兑现度：九成。 内容型页面的 bundle 体积肉眼可见地降。一个博客项目从 380KB 降到 120KB，首屏 LCP 快了 40%。这是 RSC 最硬的收益。

但有个边界情况：动态 import 的服务端组件。如果你按路由动态加载，服务端组件的"零 bundle"优势会被 loading 状态和额外的往返抵消一部分。不是不能用，是要算账。

许诺二：直接读数据库

组件里直接查 DB，不用再写一层 API：

export default async function Post({ id }) {
  // 没有 fetch，没有 API 路由，没有 loading 状态管理
  const post = await db.post.findUnique({ where: { id } });
  return <article>{post.title}</article>;
}

兑现度：六成。 API 层确实省了，但省掉的复杂度以另一种形式回来了——缓存语义。

// 这行代码，到底什么时候重新执行？
const posts = await fetch('https://api/posts', { next: { revalidate: 60 } });

fetch 的缓存、revalidate、cache: 'no-store'、unstable_cache……一个团队跟我吐槽："我们以前调 API 只用关心 URL，现在要关心这行代码的'缓存人格'。"更坑的是，默认缓存导致过好几次"改了数据页面不变"的线上事故——开发者以为是 bug，其实是缓存按设计工作。

许诺三：流式渲染

Suspense 边界让页面分块流式输出：先吐出框架和首屏，后面慢慢补。

<Layout>
  <Header />                    {/* 立刻输出 */}
  <Suspense fallback={<Skeleton />}>
    <SlowRecommendations />     {/* 2 秒后流式补上 */}
  </Suspense>
</Layout>

兑现度：七成。 首屏体验确实好，但流式对中间件和边缘运行时有要求，部署架构跟不上就用不爽。而且 Suspense 的 fallback 设计本身是个产品活——骨架屏做得丑，不如不流式。

三个真实世界的坑

坑一："use client" 边界地狱

RSC 的世界里，"use client" 是一道墙：

  • 服务端组件不能用 state、effect、浏览器 API；
  • 传给客户端组件的 props 必须可序列化——不能传函数；
  • 报错信息经常让人困惑："为什么这行不能用 useState？"

最现实的问题是：第三方库几乎全是客户端组件。图表库、富文本编辑器、拖拽库、地图——你引一个库，就要在它外面包一层 "use client"。一个中后台项目数下来，70% 的组件最后都是客户端组件，RSC 的收益被稀释得只剩数据获取层。

坑二：水合错位

服务端吐 HTML，客户端接管——两边渲染结果必须一致，否则水合错位。最经典的坑：

// ❌ 服务端和客户端渲染结果不一致
function Time() {
  return <span>{new Date().toLocaleString()}</span>; // 服务端是 UTC，客户端是本地时区
}

日期、随机数、浏览器 API 的判断，都会导致错位。团队需要建立"水合纪律"：任何依赖环境差异的渲染，都下沉到客户端组件里做。

坑三：部署架构的隐性要求

RSC 要跑在能执行 Node.js（或边缘运行时）的服务端。纯静态 CDN 托管的玩法没了，架构复杂度上了一个台阶。小团队从"Vercel 一键部署"切到"自建 SSR 集群"，运维成本是实打实的。

谁适合，谁不适合

场景 结论 原因
博客、文档、营销页 全开 RSC 内容为主，交互少，收益最大
电商详情页、信息流 推荐 首屏速度直接换转化率
中后台管理系统 谨慎 强交互，第三方库多，收益稀释
编辑器、画布、IM 别硬上 几乎全是客户端状态，RSC 是负担
纯静态展示站 没必要 直接 SSG，别引入服务端复杂度

边界划分原则：叶子交互下沉，数据获取上浮。越靠近叶子（按钮、输入框）越可能是客户端组件，越靠近根（布局、数据）越可能是服务端组件。

页面根（服务端：取数据、布局）
 └─ 文章列表（服务端：渲染）
     ├─ 点赞按钮（客户端：useState）← 交互下沉到叶子
     └─ 评论区（客户端：富文本编辑器是第三方库）

一年之后，我的判断

RSC 不是"服务端渲染"的回潮——SSR 我们十年前就玩过。它的真正创新是让"取数据"和"渲染"回到了同一个地方，干掉了中间那层胶水 API。

但它也证明了一个老规律：架构没有银弹，只有 trade-off 的搬家。RSC 把复杂度从"bundle 体积"搬到了"心智模型"，从"运行时"搬到了"构建时和部署时"。对内容型产品，这笔买卖划算；对强交互产品，可能是在花钱买罪受。

所以回到开头那五个团队：说"真香"的三个，全是内容型产品；说"迁回去"的两个，一个是低代码编辑器，一个是 IM 应用。不是技术不行，是选错了战场。

你的项目是哪种？先回答这个问题，再决定要不要上 RSC。

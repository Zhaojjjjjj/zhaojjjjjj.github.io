工程化 - CI/CD：从 30 分钟到 5 分钟，优化的是分布

"同样的代码，我本地 npm test 3 分钟跑完，CI 上跑了 28 分钟——这 25 分钟到底花在哪了？"CI 的慢几乎从来不是"测试本身慢"，而是流水线在干很多和测试无关的事：装环境、下依赖、构建、等前一个 job、跑没人看的检查。这篇把 25 分钟拆开，一项项干掉。

CI/CD：从 30 分钟到 5 分钟，优化的是分布

一个典型 Node 项目 CI 的 30 分钟构成：

jobs:
  test:
    steps:
      - uses: actions/checkout@v4
      - run: npm ci        # 3 分钟：下几百 MB 依赖
      - run: npm run build # 5 分钟：全量构建
      - run: npm test      # 20 分钟：全量测试，串行
      - run: npm run lint  # 2 分钟：排队等测试

第一原则：先量化，再动手。 CI 每个 step 都有耗时，拉出来看，瓶颈一目了然。绝大多数团队的时间分布符合 80/20——20% 的步骤吃掉 80% 的时间。

一、第零式：先做减法——最快的 job 是不跑的 job

所有"让流水线跑更快"的招式里，ROI 最高的往往是"让流水线少干活"。把每个 job 列出来问三问：

  1. 这个 job 挂了，有人看吗？ 三年前加的检查，现在没人记得为什么，挂了也没人修——信号价值为零，纯耗时；
  2. 能在本地跑吗？ lint、类型检查、单元测试，pre-commit hook 加本地校验，把反馈前移到"提交之前"；
  3. 是"每次都要"还是"每天一次就够"？ 依赖扫描、全量 e2e、性能基准，适合凌晨跑，不适合每个 PR 跑。

真实案例：一个团队从 14 个 job 删到 8 个，总时长掉 35%，一行优化代码没写。最快的代码是不跑的代码。

二、缓存、并行、增量：三招乘法

第一招：依赖缓存，ROI 之王。

- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: 'npm'  # 一行，npm ci 3 分钟 → 20 秒

按 lockfile hash 做 key，命中直接解压。三个坑：key 必须含 lockfile hash（否则"本地能过 CI 过不了"）；CI 里永远用 ci 不用 install（后者可能写回 lockfile 污染缓存）；命中率低于 90% 的缓存约等于没有，monorepo 的 node_modules 几个 GB，定期检查。

第二招：并行拆分，把串行变并行。

jobs:
  lint:   # 2 分钟
  build:  # 5 分钟
  test:   # 20 分钟 → 按 4 分片并行 → 5 分钟

测试分片的大坑是分片不均：按文件数均分，一个分片 8 分钟其他 2 分钟，总耗时被最慢的卡住。解法是按历史耗时分片（Jest 可记录单文件耗时，跑三次就准）。还有隐性坑：测试间数据污染——共用数据库、端口、文件，本地串行没事，并行互相干扰。flaky test 是并行的天敌，先修 flaky 再分片，否则省下的 15 分钟以随机失败加倍奉还。

第三招：只跑受影响的，少干事。 PR 只改 packages/ui，凭什么测 packages/api？

npx nx affected -t test --base=main

实测 90% 的 PR 只跑 10% 的测试，这是从 8 分钟到 5 分钟的关键一跃。但有两个边界：全局性变更（babel 配置、Node 升级）affected 算不出来，要配规则强制全量；affected 的误判是静默的——少跑测试 CI 全绿，bug 漏到生产。省时间的优化，失败时必须 loud：affected 配每天凌晨定时全量跑，PR 求快，定时兜底。

构建同理：Turborepo/Nx remote cache 跨机器复用产物，Docker 层缓存把"变化慢的层放前面"——90% 的构建只重跑最后一层。

三、分级 CI 与可观测性：匹配反馈节奏

很多团队的慢，源于"不管什么变更一律全量"。分级跑：

push（开发中）：lint + 相关单元测试 → 2 分钟，快速反馈
PR（待合并）：  全量测试 + affected    → 5 分钟
main（已合并）：全量 + e2e + 性能基准  → 15 分钟，严格把关

越接近合并跑得越全，离合并越远反馈越快。 开发时 2 分钟告诉你"挂了"，比 30 分钟后有用 10 倍——2 分钟时你还记得刚写了什么。PR 多了再叠合并队列（merge queue）：在"合并后的代码"上按序跑，避免"各自全绿、合进去挂了"。

优化是一次性的，劣化是持续的——对抗熵增靠可观测性：记录每个 step 耗时趋势（npm ci 从 20 秒悄悄涨到 2 分钟，图上先告诉你）；给 CI 设 SLA（"PR 流水线 P90 不超 8 分钟"，超了告警）；每季度重做一次"第零式"审计。你不测量的东西，必然慢慢变坏。

两个误区：CI 飞快但本地跑不起来——parity 比绝对速度重要，CI 省 20 分钟抵不上新人配环境 2 天；为快牺牲信号质量——砍测试关类型检查，5 分钟"全绿但其实没测"比 30 分钟有用？有害。还有上限：Amdahl 定律——并行只能加速可并行部分，先找到串行瓶颈再谈并行。

结语

30 到 5 不是某一招的神奇，是四招的乘法——注意这是"平均"耗时，优化的是分布，不是单次极值。

下周一可做的三件事，按 ROI 排序：这周加依赖缓存（一行配置，零风险，所有优化的起点）；下周拆并行加分片（动手前先修 flaky）；下个月上 affected 加分级（改造成本最高，配定时全量兜底）。

CI 优化没有银弹，只有一道算术题：缓存省掉重复劳动，并行压扁等待时间，增量减少无用功，分级匹配反馈节奏。而所有优化指向同一个目标——不是"跑得快"，是"5 分钟内告诉开发者：挂了，还是没挂"。

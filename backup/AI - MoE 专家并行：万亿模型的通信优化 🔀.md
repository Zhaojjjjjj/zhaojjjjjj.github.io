> 万亿参数 MoE 训练，最大的敌人不是算力，是通信。专家并行（Expert Parallelism）下，token 要在 GPU 之间"快递"，all-to-all 通信能吃掉 30% 的训练时间。这篇讲讲 MoE 通信优化的工程细节。

## 问题：token 的快递费

```
384 个专家，分布在 64 张 GPU 上
每个 token 要路由到 8 个专家
→ 每步训练，数十亿个 token 在 GPU 间搬运
```

all-to-all 通信的量级：

```
batch=4M tokens, hidden=8192, fp8
→ 每步通信量 ≈ 4M × 8192 × 1byte × 2（dispatch+combine）= 65GB
```

NVLink 带宽 900GB/s，看似够，但**小消息+高频次**让实际效率只有 30%。

## 优化四式

### 1. 拓扑感知路由

```
朴素：token 随机分到 64 张卡，跨机通信拉满
优化：让"经常一起被选中的专家"住在同一台机器上
```

分析路由的历史分布，把"好朋友"专家放一起。跨机（IB，400GB/s）→ 机内（NVLink，900GB/s），**通信时间砍半**。

### 2. 通信计算重叠

```
Step N：   [计算] → [通信] → [计算] → [通信]（串行）
优化后：   [计算] → [通信]
                  ↘ [下一批计算]（并行）
```

把 token 分成 micro-batch：第一批在通信时，第二批在计算。**用计算掩盖通信**，这是所有大模型训练的通用技巧，MoE 上收益最大。

### 3. 量化通信

FP8 训练已经把计算量化了，通信也可以：

```
dispatch 用 FP8（精度损失可接受）
combine 用 BF16（累加需要精度）
```

**混合精度通信**，带宽需求再降 40%。

### 4. 专家放置的动态调整

训练初期，路由分布剧烈变化；后期趋于稳定。**动态迁移专家**：把热专家复制到多张卡（expert replication），冷专家合并。DeepSeek V3 的报告里提过这招。

## 推理侧：更难

训练是"批量快递"，推理是"即时配送"：

- batch 小，通信占比更高。
- 延迟敏感，不能等"攒一波再发"。

推理 MoE 的解法是**专家亲和性调度**：同一个用户的连续请求，尽量路由到同一组 GPU，减少跨机。vLLM 和 SGLang 都在做这个。

## 一句话总结

MoE 的 scaling law 不只是"参数"，更是"通信"。2026 年，万亿模型的竞争是**互联的竞争**：NVLink、IB、拓扑、调度。记住：你的模型能有多大，取决于你的 token 能跑多快。

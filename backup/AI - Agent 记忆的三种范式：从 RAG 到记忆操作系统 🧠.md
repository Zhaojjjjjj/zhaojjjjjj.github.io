> Agent 失忆是常态：上下文窗口再大，关掉会话就忘。过去一年，Agent 记忆从"外挂向量库"演化出三种范式，分别解决不同的问题。这篇讲讲它们是什么、怎么选。

## 范式一：检索式记忆（RAG for Agent）

最直接的思路：把对话历史、工具调用记录向量化，需要时检索出来拼进 prompt。

```python
# 伪代码：最简实现
memory.add(f"{timestamp} | {role}: {content}")  # 写：向量化存入
ctx = memory.search(query, top_k=5)             # 读：相似度检索
prompt = system + ctx + user_input
```

**优点**：简单，和现有 RAG 技术栈复用，一天就能接上。

**缺点**：
- 检索质量决定一切——搜不出来等于没记；
- "记得"不等于"理解"，跨会话的身份连续性差；
- 时间久了，库里全是噪声。

**适合**：客服、问答类 Agent——记忆是"资料"，不是"人格"。

## 范式二：记忆流（Memory Stream）

灵感来自斯坦福小镇（Generative Agents）：把经历记成带时间戳的事件流，定期做一次"反思"（reflection），把零散事件提炼成高层结论。

```
事件流： 9:00 用户问了部署问题 → 9:05 解决了 → 9:30 用户又问了回滚
反思：   "用户正在上线新版本，对回滚流程不熟悉"
```

**优点**：有时间感，能形成"经验"，Agent 会表现出"成长"。

**缺点**：反思的质量不稳定；存储随时间膨胀，需要遗忘策略。

**适合**：长期陪伴、个人助理——用户要的是"它越来越懂我"。

## 范式三：记忆操作系统（Memory OS）

把记忆当成 OS 资源来管理：短期（当前上下文）、中期（工作记忆）、长期（外存/参数化），有调度、有权限、有遗忘。

```
┌─────────────┐
│ 短期：上下文窗口 │ ← LRU 淘汰
├─────────────┤
│ 中期：会话摘要   │ ← 定期压缩
├─────────────┤
│ 长期：用户画像/事实 │ ← 显式写入，需确认
└─────────────┘
```

**优点**：系统化、可工程化，7×24 运行的 Agent 需要这个。

**缺点**：复杂，实现重，小团队 hold 不住。

**适合**：长期自主运行的 Agent——比如 7×24 的运维 Agent。

## 怎么选：看运行周期

```
会话内够用？ → 什么都不做，prompt 工程解决
需要跨会话记住事？ → 范式一（RAG）
需要"越来越懂我"？ → 范式二（记忆流 + 反思）
需要长期自主运行？ → 范式三（Memory OS）
```

**别一上来就造 OS**。大部分 Agent 死在范式一和二之间——不是记忆不够强，是根本不知道要记什么。

## 三个工程建议

1. **记忆要有 TTL 和遗忘**：无限记忆 = 无限噪声。给每条记忆设有效期，过期自动降权。
2. **写记忆和读记忆用不同模型**：写（提炼摘要）用便宜模型，读（推理决策）用强模型，成本差一个数量级。
3. **记忆也要可观测**：记了什么、为什么记、什么时候被用——这三件事打日志，否则 debug 时两眼一抹黑。

## 一句话总结

Agent 记忆三范式：**RAG 解决"找得到"，记忆流解决"记得住"，记忆 OS 解决"管得好"**。选型只看运行周期：Agent 跑得越久，记忆系统越要像 OS。记住：**记忆不是存得越多越好，而是忘得越准越好**。

上周，我们的运维 Agent 半夜自动处理了一次磁盘告警，扩容、清理日志、恢复服务，一气呵成。第二天我问它："昨天半夜那个告警你是怎么处理的？"它回答："我没有昨天的记录。"

那一刻我意识到：我们给 Agent 接了最强的模型、配了最多的工具，却忘了给它"记忆"。一个没有记忆的 Agent，不管多聪明，都只是一个昂贵的单次函数调用。

## 上下文窗口不是记忆

先纠正一个常见误解：**把上下文窗口拉长，不等于给了 Agent 记忆**。

上下文窗口是工作台，不是档案室。它有三个致命缺陷：

1. **关掉就清空**——会话结束，里面的一切都消失；
2. **长度不等于重要性**——窗口越大，关键信息被淹没得越快（大海捞针问题）；
3. **没有时间感**——模型分不清"上周你说的"和"刚才你说的"，除非你显式标注。

真正的记忆系统要回答三个问题：**记什么、怎么记、什么时候忘**。过去一年，业界演化出三种范式。

## 范式一：检索式记忆

最直接的思路：把对话历史、工具调用记录向量化，需要时检索出来拼进 prompt。

```python
# 记忆的写入：每轮对话结束后
memory.add(text=f"{timestamp} | {role}: {content}", metadata={"session": sid})

# 记忆的读取：生成回答前
related = memory.search(query=user_input, top_k=5)
prompt = system_prompt + "\n".join(related) + user_input
```

这本质上是把 RAG 用在了 Agent 自己身上。优点是简单——有向量数据库就能跑，一天接上。

但它有三个坑，个个致命：

**第一，检索质量决定一切。** 搜不出来等于没记。而用户的问题和当初的记录，措辞往往完全不同。"上次那个部署问题"和"kubectl apply 报 ImagePullBackOff"，向量相似度可能低得可怜。

**第二，没有时间感。** 三个月前的偏好和昨天的偏好冲突时，它不知道该信哪个。检索式记忆是"一堆便签"，不是"一个人的人生"。

**第三，噪声膨胀。** 跑三个月，库里有几十万条记录，检索出来的 top_k 一半是垃圾。记忆系统最大的敌人不是遗忘，而是**记了太多没用的**。

**适合**：客服、问答类 Agent。记忆在这里是"资料库"，不是"人格"。

## 范式二：记忆流

灵感来自斯坦福小镇（Generative Agents）：把经历记成带时间戳的事件流，定期做一次"反思"（reflection），把零散事件提炼成高层结论。

```
事件流：
  09:00 用户问了如何回滚 deployment
  09:05 用 kubectl rollout undo 解决了
  09:30 用户又问了如何查看 rollout 状态

反思（每天凌晨跑一次）：
  "用户正在上线新版本，对回滚流程不熟悉，
   下次主动提示 --record 参数"
```

反思是关键一跃：**记忆不再是原文的堆积，而是经验的沉淀**。Agent 会表现出"成长感"——这是用户觉得"它越来越懂我"的来源。

但反思机制有两个软肋：

**反思的质量不稳定。** 用便宜模型做反思，提炼出来的结论可能是幻觉；用贵模型，成本又扛不住。一个折中：反思用中等模型，但给反思加"证据链"——每条结论必须引用原始事件，引用不上就丢弃。

**存储随时间膨胀。** 事件流只增不减。需要配套的压缩策略：30 天前的原始事件可以删，只保留反思结论；反思结论再往上，还可以做"月度总结"。

**适合**：长期陪伴、个人助理。用户要的不是"记得住"，是"有默契"。

## 范式三：记忆操作系统

把记忆当成 OS 资源来管理：分层、调度、权限、遗忘。

```
┌─────────────────────────────┐
│ 短期记忆：当前上下文窗口        │  策略：LRU，自然淘汰
├─────────────────────────────┤
│ 中期记忆：会话摘要 / 任务状态   │  策略：定期压缩，保留 30 天
├─────────────────────────────┤
│ 长期记忆：用户画像 / 领域事实   │  策略：显式写入，需用户确认
└─────────────────────────────┘
         ↓ 统一的读写接口
    遗忘引擎：Ebbinghaus 曲线 + 重要性评分
```

这套范式最有野心，也最重。它要解决的是**7×24 小时自主运行**的 Agent 的记忆问题——比如一个长期值守的运维 Agent，三个月后还记得"这个集群的 etcd 曾经脑裂过"。

OS 范式多出来的两个维度，是前两种范式没有的：

**权限**：什么能记，什么不能记。用户的密码、身份证号，写进记忆就是数据泄露。记忆系统需要 PII 过滤，这是合规红线。

**遗忘算法**：借鉴艾宾浩斯遗忘曲线——记忆的重要性随时间衰减，每次被"想起"就加强一次。从不被想起的记忆，自动沉底。这比"一刀切的 TTL"聪明得多。

**适合**：长期自主运行的 Agent。小团队别一上来就造 OS，hold 不住。

## 三个容易踩的坑

不管选哪种范式，这三个坑是共通的：

**1. 只存不忘。** 这是 90% 自研记忆系统的死因。记忆的信噪比随时间单调下降，不做遗忘，三个月后系统就不可用了。**遗忘不是缺陷，是功能。**

**2. 记忆没有版本。** 用户上个月说"用 Python"，这个月说"切 Go 了"。两条记忆打架，Agent 该信哪个？记忆需要版本号和冲突解决策略——最简单的：新记忆覆盖旧记忆，但保留变更记录。

**3. 记忆不可观测。** Agent 做了一个奇怪的决策，你问它为什么，它说"根据我的记忆"。哪些记忆？什么时候写入的？可信度多高？**记忆的读写必须打日志**，否则 debug 时两眼一抹黑。

## 怎么选

别问"哪种最强"，问"我的 Agent 要跑多久"：

- 会话内能搞定——什么都不用做，prompt 工程解决，别过度设计；
- 需要跨会话记住事——范式一，RAG 那套直接复用；
- 用户期待"越来越懂我"——范式二，记忆流加反思；
- 7×24 自主运行——范式三，Memory OS。

一个务实的演进路线：**先上范式一，跑三个月，看到记忆的信噪比在下降，再引入范式二的反思做压缩；只有当你要做长期自主 Agent 时，才考虑范式三**。记忆系统和缓存系统一样，都是先简单、再按需复杂。

记忆系统的终极考验不是记住，而是忘掉。一个好的 Agent，应该像一个好的同事：记得关键的事，忘了细枝末节，而且你问它"为什么记得这个"，它能说出理由。

> GPT-4.1 发布时最抓眼球的数字不是 SWE-bench 55%，而是 100 万 token 上下文——而且价格还比 4o 便宜 26%。这篇算一算，百万上下文背后到底要付出什么工程代价。

## 先算一笔账：KV Cache

Transformer 推理时，每个 token 的 Key 和 Value 都要缓存，显存占用公式：

```
KV Cache = 2 × 层数 × hidden_dim × seq_len × 精度字节数
```

按一个 70B 级模型估算（80 层，hidden 8192，FP16）：

```
2 × 80 × 8192 × 1,000,000 × 2B ≈ 2.6TB
```

**2.6TB**——单卡装不下，8 卡 H100（640GB）也装不下。这就是为什么"支持 1M 上下文"本身就是一种工程宣言。

## 注意力是 O(n²)

Self-attention 的计算量随序列长度平方增长：

```
1M tokens → 每层注意力矩阵是 10¹² 个元素
```

就算有 FlashAttention 把 IO 复杂度降下来，计算量本身是省不掉的。1M 上下文的 prefill，烧的都是真金白银的 FLOPs。

## 工程上怎么扛下来的

几招组合拳，缺一不可：

1. **GQA（Grouped Query Attention）**：KV 头分组共享，KV Cache 直接砍掉 3/4。这是 2024 年后长上下文模型的标配。
2. **PagedAttention**（vLLM）：把 KV Cache 按块管理，像操作系统管内存页一样，碎片率大降。
3. **RoPE 外推 / YaRN**：位置编码插值，让训练时没见过的长度也能工作——但外推质量衰减是玄学，各家调参见真章。
4. **Prompt Caching**：前缀缓存，重复的 system prompt / 文档只算一次。OpenAI 的降价 26%，很大一部分是缓存和工程优化吃掉的成本。

## "支持"不等于"好用"

两个扎心的事实：

- **Lost in the Middle**：模型对上下文中间部分的信息利用率显著低于首尾。1M 上下文里，中间 800K 很大程度上是"心理安慰"。
- **Needle-in-a-haystack 满分 ≠ 真实任务好用**：大海捞针测的是检索，真实的长文档推理（多跳、对比、综合）衰减要严重得多。

## 给开发者的建议

1. **别把 1M 当 1M 用**：RAG + 长上下文是组合技，不是替代关系。先检索再精读，比无脑全量塞便宜一个数量级。
2. **算钱**：output token 比 input 贵得多，长上下文场景下，让模型"少说话"是第一优化。
3. **测真实任务**：拿你自己的文档跑多跳问答，别信厂商的 needle 分数。

## 一句话总结

百万上下文是工程奇迹，也是营销话术——奇迹在于 GQA + PagedAttention + 缓存把不可能变成了可能，话术在于"支持的长度"和"有效的长度"之间，还差着一个 Lost in the Middle。用之前，先算账。

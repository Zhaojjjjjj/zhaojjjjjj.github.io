> 先记住一个数字：**2.6TB**。这是一个 70B 级模型在 1M token 上下文下，光 KV Cache 就要吃掉的显存。8 张 H100（640GB）也装不下。"支持 1M 上下文"这句话背后，是一整套拿显存、带宽和真金白银堆出来的工程。

## KV Cache：每个 token 都在交"房租"

Transformer 做自回归推理时，每生成一个 token，都要回顾之前所有 token 的 Key 和 Value。重复计算太贵，于是把它们缓存下来——这就是 KV Cache。它的大小是个死公式：

```
KV Cache = 2（K 和 V）× 层数 × hidden_dim × seq_len × 精度字节数
```

代入一个 70B 级模型的典型配置（80 层，hidden_dim 8192，FP16）：

```
2 × 80 × 8192 × 1,000,000 × 2B ≈ 2.62TB
```

**每个 token 都在显存里交房租，而且房租只涨不跌**——序列越长，Cache 越大，线性增长，没有上限。这就是长上下文第一个反直觉的真相：瓶颈不在"模型聪不聪明"，在"显存够不够大"。

## 真正的杀手不是容量，是带宽

但 2.6TB 只是故事的一半。假设你真有 2.6TB 显存（比如一堆机器做张量并行），推理就能跑顺了吗？不能——因为 decode 阶段的瓶颈是**显存带宽**，不是容量。

自回归生成时，每吐一个 token，GPU 都要把**全部** KV Cache 从显存（HBM）里读一遍送进计算单元。算一下：

```
2.6TB ÷ 3TB/s（H100 的 HBM 带宽）≈ 0.87 秒 / token
```

**每秒只能吐 1 个 token**——这还是理论上限，没算多卡通信的开销。实际上没人用单卡跑 1M——要做张量并行/流水线并行，把 2.6TB 分到 8 张卡上。但并行引入了新的税：**每层 attention 的 all-reduce 通信**。序列越长，通信量越大，8 卡的利用率可能掉到 50% 以下。**你以为你在买显存，其实你还在买 NVLink 带宽**。

1M 上下文的 decode，本质上是在用整个机架的 HBM 带宽，一个字节一个字节地"回忆"过去。这就是为什么长上下文推理贵得离谱：你花的不是存储的钱，是**每次生成都要全量扫描**的钱。

而 prefill（处理输入 prompt）阶段恰恰相反：它是计算密集型的。Attention 的计算量是 O(n²)：

```
1M tokens → 每层的注意力矩阵是 10¹² 个元素
```

FlashAttention 把 IO 复杂度降下来了（分块计算，不 materialize 完整的注意力矩阵），但**计算量本身一分都省不掉**。1M 上下文的 prefill，烧的是实打实的 FLOPs。所以长上下文推理的完整画像是：**prefill 吃算力，decode 吃带宽**——两头都要交税，一头都躲不掉。

## 工程上怎么扛下来的：四件套

厂商们是靠组合拳把 1M 从"不可能"变成"很贵但能卖"的，缺一不可：

**1. GQA：KV 头分组共享。** 传统的 MHA 每个 Query 头配一对 KV 头；GQA 让多个 Query 头共享一组 KV 头。8 组 KV 头的配置下，KV Cache 直接砍掉 3/4。这是 2024 年之后长上下文模型的标配——不是优化，是入场券。没有 GQA，1M 上下文连想都不用想。

**2. PagedAttention（vLLM）：把 KV Cache 当内存页管。** 传统实现给每个请求预分配连续显存，碎片率高得吓人。PagedAttention 按块（block）分配，像操作系统管内存页一样，碎片率大降，吞吐直接翻倍。这是推理框架层的胜利——不改模型，只改"内存管理"，就把利用率抬了一个台阶。

**3. RoPE 外推 / YaRN：位置编码的"续命"。** 模型训练时只见过 128K 的长度，推理时要撑到 1M，位置编码会"没见过这么大的数字"。YaRN 这类插值方法让外推成为可能——但外推质量的衰减曲线是玄学，各家的温度、缩放参数都是真金白银调出来的。同一份 YaRN 代码，调参水平不同，1M 处的质量天差地别。

**4. Prompt Caching：重复的前缀只算一次。** System prompt、常用文档，前缀命中缓存就不用重算 prefill。之前某家"1M 上下文还降价 26%"的发布，业内都清楚：很大一部分是缓存和工程优化吃掉的成本——**降价的不是智能，是工程**。

## 压缩 KV：房租太贵就合租

既然 KV Cache 是按 token 交房租，省房租就成了显学：

- **量化**：KV 从 FP16 压到 INT8 甚至 INT4，Cache 直接减半再减半。代价是精度损失——好在 K 和 V 对量化相对不敏感，这是少数"免费午餐"之一。
- **Eviction（驱逐）**：StreamingLLM 发现注意力有个"注意力汇点"现象——最初的几个 token 权重奇高，留着它们，加上一段滑动窗口，剩下的 KV 扔掉，效果几乎不降。H2O 更进一步，按注意力分数动态淘汰"不重要"的 KV。**这本质上是在承认：不是所有 token 都值得交房租。**
- **MLA（DeepSeek 的路线）**：把 KV 压缩成低秩 latent 向量再缓存，Cache 体积直接降一个数量级。这是架构级的解法，不是补丁。

三条路线的共识是：**KV Cache 里有大量冗余**，2.6TB 这个数字是"naive 实现"的上限，不是物理极限。但也别乐观过头——压缩省的是容量，decode 时"每个 token 全量读一遍"的带宽税，压缩只能等比缓解，消不掉。

## O(n²) 有没有解：稀疏注意力

注意力矩阵是 n×n 的，但里面大部分是接近零的权重——**稠密计算里藏着稀疏的真相**。于是有了稀疏注意力：

- **Sliding window**：每个 token 只看邻居，复杂度 O(n×w)，Mistral 早期就这么干；
- **NSA / MoBA**：把 attention 也做成 MoE——每个 query 只去 top-k 个 KV 块里找，把 O(n²) 降到近似 O(n log n)。

但稀疏是有代价的：**你省掉的计算，可能是模型本来要用的长程依赖**。needle 任务在稀疏注意力下最容易翻车——针恰好落在被剪掉的块里，就永远找不到了。所以稀疏注意力至今没成为 1M 模型的主流：**省的是确定的成本，赌的是不确定的质量**。这笔账，厂商比你更会算。

## "支持"和"好用"之间，隔着两个扎心事实

工程奇迹归奇迹，但有两个事实，厂商发布会不会告诉你：

**第一，Lost in the Middle。** 多项研究证实：模型对上下文中间部分的信息利用率，显著低于开头和结尾。1M token 里，中间那 800K 很大程度上是"心理安慰"——放进去了，但模型没怎么看。**你买的 1M，有效的可能只有首尾的 200K。** 这不是某个模型的 bug，是注意力机制在超长序列下的系统性行为。

**第二，needle 满分 ≠ 真实任务好用。** 大海捞针（needle-in-a-haystack）测的是"找得到"，而真实任务要的是"找得到 + 推得对"：多跳推理、跨文档对比、综合归纳。在这些任务上，长上下文的衰减比 needle 分数难看得多。**检索能力不等于推理能力**，拿 needle 分数当选型依据，等于拿百米成绩选马拉松选手。

## 算一笔总账：128K vs 1M

假设一个文档问答场景，两种方案：

- **方案 A：全量塞 1M**——prefill 要处理 1M token（O(n²) 的算力税），decode 时每次生成都扫描 2.6TB KV（带宽税）。延迟高、贵，但"不会漏"。
- **方案 B：RAG 捞 32K + 长上下文精读**——检索花零头，模型只读 32K。KV Cache 从 2.6TB 降到 80GB 级别，decode 带宽压力降 30 倍。

实测里，方案 B 的答案质量在多数任务上**不输甚至更好**（注意力没被稀释），成本是方案 A 的零头。中文社区吵了很久的"RAG 已死"，纯属伪命题——正确的分工是 **RAG 负责"找"，长上下文负责"读"**。长上下文真正的用法，是"读得深"，不是"塞得多"。等哪天 1M 的 decode 带宽成本降一个数量级，这个结论才值得重估。

## 什么时候 1M 真的值：三个场景

不是所有任务都需要，但有三类场景，长上下文是真刚需：

- **整个代码库的重构**：Agent 要同时看几十个文件的调用关系，RAG 捞出来的片段是碎的，长上下文一次吃下整个模块，跨文件重命名、接口迁移这类任务质量明显更高；
- **长文档的综合研读**：几百页财报、论文综述——问题本身就是"把分散在 200 页里的信息拼起来"，检索式 RAG 会把拼图拆碎；
- **多轮复杂 Agent 任务**：循环跑 50 轮，每轮的 observation 都要留着，长上下文是循环的"记忆体"。

共性是：**任务本身要求"全局视野"，而不是"精准定位"**。前者用长上下文，后者用 RAG。分不清这个边界的人，要么在浪费钱，要么在浪费质量。

## 给开发者的三条铁律

1. **别把 1M 当 1M 用。** RAG 和长上下文是组合技，不是替代关系：先检索出 top_k 再精读，比无脑全量塞便宜一个数量级，还更准。长上下文应该是你的"弹药库"，不是"默认弹夹"——默认弹夹装 32K，弹药库留 1M，按需取用。
2. **算 decode 的账，不是 prefill 的账。** Input token 看似便宜，但长上下文场景下，真正的成本在"每个输出 token 都要全量扫描 KV"的 decode 阶段。让模型少说话（短输出、少轮次），是第一优化：能流式就别等整段，能要摘要就别要全文。
3. **用你自己的任务测。** 拿你的真实文档跑多跳问答，画出"长度-质量"衰减曲线，找到你业务的拐点。厂商的 needle 分数，看看就好。
4. **留"有效余量"。** 既然中间部分利用率低，重要信息就别放中间：关键指令放 system prompt（开头），关键数据放结尾。这是长上下文时代的土办法，但实测有效。

百万上下文是工程奇迹，也是定价话术——奇迹在于 GQA + PagedAttention + 缓存把不可能变成了可能，话术在于"支持的长度"和"有效的长度"之间，还差着一个 Lost in the Middle。它不是骗局，但它是一张**需要你会算账才敢刷的卡**：算清楚 KV 的房租、带宽的过路费、注意力的平方税，再决定塞多少进去。不会算账的人，买的不是 1M 上下文，是 1M 的幻觉。

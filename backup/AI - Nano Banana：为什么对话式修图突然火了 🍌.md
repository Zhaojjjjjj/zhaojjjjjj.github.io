> Google 的 Gemini 2.5 Flash Image（代号 Nano Banana）没有发论文、没有刷榜，却成了那年最出圈的 AI 产品：人们用它给照片换衣服、把合影 P 进电影海报，而且多轮修改不崩。这篇讲讲它为什么火——以及火的到底是什么。

前几天刷朋友圈，看到一张"电影海报"：朋友的全家福，主角们站在黄昏的海滩上，色调、光影、字体排印都像模像样。评论区都在问用的什么 App。朋友回了一句："就跟它聊了五分钟。"

"聊了五分钟"——这五个字，就是 Nano Banana 火的全部秘密。

## 火的不是技术，是交互

Nano Banana 的底层技术（图像生成/编辑）并不首创，Midjourney、Flux 都能改图。它真正的创新是**交互范式**：

```
之前（抽卡式）：
  上传图 → 写 prompt → 出图 → 不满意 → 重写 prompt → 从头生成
  每一轮都是独立事件，上一轮的成果全部作废

Banana（对话式）：
  上传图 → "把背景换成海滩" → 出图
        → "再把衣服换成红的" → 在上一版基础上改
        → "色调再暖一点" → 继续在上一版基础上改
  每一轮都是增量，人物、风格、构图全程保持一致
```

修图从"抽卡"变成了"聊天"。**"再"这个字，是整个产品里最重要的一个字**——它意味着系统记住了上一版，理解了"在……基础上改"。

为什么之前没人做成？因为"在上一版基础上改"这句话，藏着三个硬骨头。

## 硬骨头一：一致性——第 5 轮的人脸不能变

多轮编辑最难的是**一致性**：改第 5 轮背景的时候，第 1 轮的人脸、衣服、构图，一个都不能动。

传统拼接式管线（LLM 理解指令 + 生图模型执行）在这里会经历**三次转述损耗**：

```
用户指令 → LLM 理解成文字描述 → 生图模型按文字重画 → 细节丢失
"把背景换成海滩" → "一张全家福，背景是海滩" → 重画整张图
结果：背景换了，人脸也"换"了——因为是重新生成的
```

Nano Banana 的做法是**原生多模态**：图像和文本在同一个 Transformer 里，图像本身就是 token。编辑时，原图 token + 历史编辑 token + 新指令一起进模型：

1. **自注意力就是记忆**：新图的每个 token 都能"看到"原图的所有细节，不需要转述；
2. **原图 latent 做强条件锚定**：diffusion 去噪时，原图的隐表示像锚一样拽住生成过程，不该变的地方不许漂；
3. **增量编辑而非重绘**：模型学的是"给定原图和指令，输出差异"，而不是"给定描述，从头画一张"。

对比下来，拼接式方案的信息损耗发生在"转述"环节，原生多模态**没有转述环节**——这是它多轮不崩的物理基础。

## 硬骨头二：指代消解——"再把衣服换成红的"

对话式交互带来一个纯 NLP 问题：**省略和指代**。

- "再把衣服换成红的"——"衣服"指谁的衣服？（照片里三个人的）
- "色调再暖一点"——"再"是相对上一版，不是相对原图
- "把他 P 掉"——"他"是左边那个还是右边那个？

人类觉得自然的表达，对机器全是歧义。Nano Banana 能 work，是因为多模态模型把**图像当成了共同的上下文**："衣服"指谁，看图就知道；"他"是哪个，看图就知道。**图像消解了语言的歧义**——这是"对话式修图"成立的前提，也是纯文本 Agent 玩不转这类任务的原因。

## 硬骨头三：版本管理——撤销是刚需

对话式产品的后端，本质上是一个**版本管理系统**：

```
v0 原图
v1 "背景换成海滩"
v2 "衣服换成红的"
v3 "色调暖一点"  ← 用户：还是 v2 好
→ 回退到 v2，从 v2 fork 出 v4
```

每次编辑是一个 commit，可以回退、可以 fork、可以对比。没有版本管理，"多轮"就是灾难——用户第 5 轮说"还是第 2 版好"，你拿不出来，前面全白聊。

做对话式产品的团队，**先设计版本模型，再设计生成模型**。状态管理是 1，生成质量是后面的 0。

## 为什么是 Google 做成了

三个条件，缺一不可：

**1. 数据：隐形的护城河。** Gemini 训练时见过海量"图像 + 编辑指令"对——不是"图像 + 描述"，是"改图前 + 改图后 + 人是怎么说的"。这种三元组数据，公开数据集里几乎没有，只能靠产品级流量积累。

**2. 分发：0 门槛。** 直接塞进 Gemini App，用户不用下载新东西、不用学 prompt。技术再强，没有分发也是白搭。AI 产品的历史一再证明：**分发是技术的一部分**。

**3. 统一多模态预训练是前提。** 图像和文本在同一个模型里从头一起训练，而不是后期拼接。拼接式架构永远有"转述"环节，一致性天花板就是低一截。架构选择，决定了产品形态的上限。

时机反而是最不重要的——"AI 修图"的需求一直都在，只是之前没有对的交互。

## 硬币的另一面

火归火，三个问题值得冷静看：

**1. 一致性的另一面是 deepfake。** "多轮修改人物不崩"这个能力，用在换脸、伪造照片上同样好用。技术不分善恶，但产品需要分——水印、来源标注、敏感人物限制，这些不是"政治正确"，是这类产品的生存必需。

**2. 审美在被平均化。** 当"电影海报风"一句话可得，朋友圈很快会出现一千张同款海报。工具拉平了执行的门槛，**稀缺的变成了审美本身**——知道"改成什么样"，比"会不会改"值钱得多。

**3. 复杂变更仍然弱。** 换背景、换衣服、调色调是强项；但"把站姿从坐着改成跑步"这种涉及人体结构、透视、遮挡的大改，依然容易崩。编辑的复杂度天花板还在，只是比以前高了一大截。

## 编辑强度的光谱：越往右越难

不是所有"改"都一样难。按编辑强度排一条光谱：

```
调色/滤镜 < 换背景 < 换衣物/物体 < 改姿态/结构 < 跨图融合
   易 ──────────────────────────────→ 难
```

- **左端（调色、滤镜）**：像素级变换，一致性几乎免费，传统工具也能做；
- **中段（换背景、换物体）**：需要语义理解——"衣服"在哪、"背景"的边界到哪。这是原生多模态的主场，拼接式管线在这里开始掉链子；
- **右端（改姿态、跨图融合）**：把坐姿改成跑步，涉及人体结构、透视、遮挡重建；把 A 照片的人放进 B 场景，还要统一光照和色温。**这是当前的天花板**，Nano Banana 在这里也会崩。

这条光谱是给开发者的选型尺：你的场景落在哪个位置，决定了你需要什么级别的模型。**别拿改姿态的需求，去测只能换背景的模型，然后说"AI 修图不行"。**

## prompt 死了吗

对话式修图还杀死了另一个东西：**prompt engineering 的旧范式**。

之前，prompt 是"一次写对"的艺术——写得越长、越精确越好，社区里流传着各种"咒语"。对话式交互下，表达变成了迭代的：先说个大概，看结果再补细节。"写 prompt"变成了"聊需求"。

但 prompt 没死，它换了个位置：

1. **首轮表达能力更重要了**：第一句话的质量，决定了你需要迭代几轮。会"聊"的人 2 轮搞定，不会"聊"的人 10 轮还在打转；
2. **系统 prompt 比用户 prompt 更重要**：幕后的 system prompt 定义了模型的"编辑人格"——保守还是激进、什么能改什么不能改。产品之间的差异，越来越藏在这里；
3. **岗位描述要改写**：prompt 工程师从"写咒语"变成"设计对话流程"——设计追问、澄清、确认的话术，比写长 prompt 值钱。

## 对开发者的三条启示

**1. 交互 > 算法。** Banana 的模型不是最强的，但交互是最对的。AI 产品的胜负手，越来越多在 UX 而不在参数量。下次立项，先问"交互范式对了吗"，再问"模型够强吗"。

**2. 一致性是所有"改"场景的命门。** 改图、改代码、改文档，第一原则都是"不该改的地方别动"。做代码 Agent 的团队应该深有体会：一个 diff 改了 50 行，其中 40 行是无关格式变动，用户信任直接归零。**最小 diff 原则**，是编辑类 AI 的通用军规。

**3. 状态即版本。** 任何多轮、对话式的产品，后端都要按版本系统设计：commit、回退、fork、对比。把"会话状态"当成"版本链"来建模，很多看似复杂的需求（"回到第 2 版再改"）会自然有解。

**4. 编辑历史是数据金矿。** 每次"用户说改、模型改、用户说还是上一版好"，都是一条高质量的人类偏好数据——RLHF 梦寐以求的东西。对话式产品天然在收集审美反馈：**把版本链存下来，它就是你下一代模型的训练集**。做产品时顺手把数据飞轮埋进去，是 Banana 这类产品最被低估的资产。

## 最后一个问题

当"说句话就能改图"变成默认交互，**下一个被"对话式"重做的创作工具是什么？**

写代码已经在路上了（结对编程 Agent 本质上就是"对话式改代码"），剪视频、做 3D、调混音还会远吗？每一个"抽卡式"的创作工具——调参、渲染、等结果、不满意重来——都值得被问一遍：能不能变成"聊天"？

以及更扎心的一问：当修改的门槛降到一句话，**什么能力反而变稀缺了？** 我的答案是两样：知道"改成什么样"的审美，和知道"为什么这样改"的判断。工具负责执行，人负责品味——这个分工，Nano Banana 只是让它更明显了一点。

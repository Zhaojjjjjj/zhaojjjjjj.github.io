# 时区 bug：每天差 8 小时，跑了三个月没人发现

凌晨 3 点，PagerDuty 把我叫醒：对账任务没跑，资金缺口告警响了 20 分钟。

我爬起来查日志，越看越不对劲——任务跑了，**每天都跑，就是每天 10 点跑**。定时任务设的是"每天凌晨 2 点"，它每天 10 点执行，跑了三个月，今天资金方对账对不上，才第一次被发现。

三个月，每天差 8 小时，没人发现。因为任务"看起来"一切正常：成功率 100%，日志干净，只是**在错误的时间，做着正确的事**。时区 bug 就是这样：不崩、不报错、不抛异常，只是默默地错。而等你发现时，它已经错了很久。

# 一、嫌疑一：cron 的"默认时区"

```javascript
// 需求：每天北京时间凌晨 2 点跑
cron.schedule('0 2 * * *', task);
// 实际：每天 UTC 凌晨 2 点跑 = 北京时间 10 点
```

大多数 cron 库**默认用系统时区**，服务器通常是 UTC。`0 2 * * *` 不带任何时区信息——它问的是"2 点"，但没说是"哪里的 2 点"，于是用了服务器的 2 点。

```javascript
cron.schedule('0 2 * * *', task, {
  timezone: 'Asia/Shanghai',  // 永远不要依赖默认
});
```

但还有第二层：K8s CronJob 的 `timeZone` 字段 1.27+ 才支持，不写默认用 kube-controller-manager 的时区。node-cron、bullmq、系统 crontab、云厂商触发器——**每一层的默认值都要亲手确认**。铁律：时区必须显式声明，链路上的每一层都是。

# 二、嫌疑二：Date 的解析玄学

```javascript
new Date('2025-11-29')        // UTC 午夜！不是本地午夜
new Date('2025-11-29T02:00')  // 本地时间（没有 Z 后缀）
new Date('2025/11/29')        // 本地时间，但 Safari 直接解析失败
```

`'2025-11-29'` 这种日期-only 字符串，ES 规范明确按 **UTC** 解析——全世界前端 collectively 踩过最多的坑。**同一个意思，三种写法，三种结果。**

三条军规：**存储用 UTC**（数据库永远存 UTC 时间戳）；**传输用带时区的 ISO8601**（`2025-11-29T02:00:00+08:00`，裸字符串的时区是"阅读理解题"，而阅读理解一定有人做错）；**计算用库**，别手算 `+8*3600*1000`。

手算的本质问题：**你把"时区"压缩成了一个数字（偏移量），但时区不是数字，是规则**。`America/New_York` 一年里在 -5 和 -4 之间横跳，一个数字装不下。`dayjs.tz(..., 'America/New_York')` 背后是完整的 IANA 时区数据库——**让库去查表，别自己当表**。

# 三、嫌疑三：数据库的时区观

Postgres 里两个类型，名字像双胞胎，行为是仇人：

```sql
-- timestamptz：存 UTC，取出按连接时区转换（推荐）
created_at TIMESTAMPTZ DEFAULT now();
-- timestamp：存什么取什么，"naive" 时间，时区信息写入即丢失
created_at TIMESTAMP DEFAULT now();
```

用 `timestamp` 存"2025-11-29 02:00:00"，半年后没人答得上来"这是哪个时区的 2 点"。MySQL 更刺激：`TIMESTAMP` 按连接时区自动转换，`DATETIME` 不转——应用和 MySQL 的 `time_zone` 不一致时，写入读取经过两次方向相反的转换，**只在某些部署环境出现**，本地永远复现不了。

原则：**`timestamptz` + 连接时区统一 UTC**，把"转换"收敛到应用层的展示逻辑，别让每一层都自作主张转一次。

# 四、终极 Boss：夏令时

前面都是"差 N 小时"的线性问题，夏令时让"一天 24 小时"这个假设本身失效：

```
美国 2025-03-09：凌晨 2:00 直接跳到 3:00 → 设在 2:30 的任务这天不会跑
美国 2025-11-02：凌晨 2:00 回拨到 1:00 → 设在 1:30 的任务这天跑两次
```

这是**逻辑上无解**的：2:30 在那一天根本不存在。而"跑两次"更阴险——对账任务跑两次，可能就是**重复打款**。解法只有一个：**跨国业务的定时调度，一律用 UTC**。UTC 没有夏令时，一天永远 86400 秒。"本地时间"只留给展示层。

衍生坑：`"3 天后" ≠ "+72 小时"`（跨切换日时，用库的 `add(3, 'day')` 按日历日算）；日志时间戳全链路统一 UTC+ISO8601（三份日志时区不一致，事故时连时间线都排不出来——**不一致的日志不是信息，是噪音**）。

# 结语：排查清单

下次差 8 小时，按这个顺序查：

> 1. **调度层**：cron 时区显式声明了吗？K8s CronJob 的 `timeZone` 写了吗？
> 2. **系统层**：服务器时区、Node 进程 `TZ`、容器 `/etc/localtime`——三者可能各说各话；
> 3. **应用层**：所有 `new Date(字符串)` 带时区吗？搜 `getTimezoneOffset`——凡出现这个 API 的地方，都是前人被坑过的证据；
> 4. **存储层**：`timestamptz` 还是 `timestamp`？连接时区是 UTC 吗？
> 5. **展示层**：页面时间经过了正确的时区转换吗？

以及最重要的测试策略：**把测试环境的系统时钟拨到 DST 切换日前一天，跑一遍全量定时任务**。时区 bug 平时潜伏，只在切换日爆发——而切换日一年只有两天。打开你的项目搜一下 `new Date(`，数数有多少裸字符串；再搜 `schedule(`，看几处写了 `timezone`。如果这两个数字让你心里一紧，恭喜，你刚找到了下一个凌晨 3 点告警的地址。

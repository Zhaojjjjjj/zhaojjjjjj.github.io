> 2025 年，Anthropic 的 Prompt Caching 和 OpenAI 的 Prompt Cache 开始成为"默认优化"。原理不复杂，但用好它能把 API 账单砍掉一个数量级。这篇讲透它的机制和最佳实践。

## 核心思想

大模型 API 调用中，大量 token 是重复的：system prompt、 few-shot 示例、长文档。每次调用都重新算一遍 prefill，又贵又慢。

**Prompt Caching**：把 prompt 的前缀缓存起来，下次调用如果前缀相同，直接复用 KV Cache，跳过重复计算。

```
调用 1: [system(5K) + docs(50K) + question1] → 全量计算，缓存前缀
调用 2: [system(5K) + docs(50K) + question2] → 命中缓存，只算 question2
```

## 缓存的粒度：前缀匹配

关键细节：**缓存是按前缀精确匹配的**。`[A+B+C]` 和 `[A+B+D]` 只能复用 `A+B` 的部分，C 的计算省不掉。

这意味着 prompt 的**顺序就是性能**：

- ✅ 把不变的部分放前面：system prompt → 文档 → 工具定义
- ✅ 把变化的部分放最后：用户问题、对话历史
- ❌ 在 system prompt 里塞时间戳、随机数——每次前缀都不同，缓存永远命中不了

## 各家的实现差异

- **Anthropic**：显式 `cache_control` 标记，最多 4 个断点，缓存 5 分钟（可续）。命中时 input 按 0.1x 计费——**便宜 90%**。
- **OpenAI**：自动缓存（1024 token 起），按路由自动命中，无需标记。折扣力度小一些，但零心智负担。
- **DeepSeek**：硬盘缓存，命中 0.1x，miss 1x。上下文命中还有额外折扣。

## 实测建议

1. **断点放在"稳定边界"**：system prompt 结尾、文档结尾、工具定义结尾，各打一个。
2. **工具定义很占地方**：MCP 接十几个 server 时，工具 schema 可能上万 token——缓存它是第一优先级。
3. **长文档问答**：50K 文档 + 连续提问的场景，缓存命中率 95%+，成本直接除以 10。
4. **监控命中率**：Anthropic 返回 `cache_read_input_tokens`，盯着这个数字，低于 80% 就去查 prompt 顺序。

## 坑

- **缓存不是免费的**：Anthropic 写缓存要收 1.25x（5 分钟 TTL）。调用频率太低的话，写缓存的钱比省的多——适合高频场景。
- **安全性**：缓存的 KV 是按组织隔离的，不会串。但别在缓存前缀里放用户隐私——复用边界要想清楚。

## 一句话总结

Prompt Caching 是 2025 年最被低估的优化：零算法改动，纯工程红利。记住一句话——**prompt 的顺序就是钱，越稳定的放越前**。

同一份 5 万字的 system prompt，你这个月为它付了 127 次钱——其中 126 次，算出来的结果一模一样。

这不是夸张。任何一个高频调用大模型 API 的服务都在干这件事：每次请求都把 system prompt、工具定义、few-shot 示例原样发过去，模型每次都老老实实从头算一遍 prefill，然后给出和你上次几乎相同的中间表示。你付的不是"思考"的钱，是"重复"的钱。

Prompt Caching 就是来终结这种浪费的：**把 prompt 的前缀缓存起来，前缀相同就直接复用 KV Cache，跳过重复计算**。原理不复杂，但把它用好的团队，API 账单普遍降了一个数量级——它是近年来最被低估的纯工程红利。

## 先理解你在为什么付费

一次 API 调用的计算分两步：

1. **Prefill**：把整个 prompt 并行算一遍，生成 KV Cache。这是 O(n²) 的 attention 计算，prompt 越长越贵；
2. **Decode**：一个 token 一个 token 地生成，复用 prefill 的 KV Cache。

Prompt Caching 省的是第一步。调用 1 全量计算并缓存前缀，调用 2 如果前缀相同，直接加载缓存的 KV Cache，只算新增部分：

```
调用 1: [system(5K) + docs(50K) + question1] → 全量计算，缓存 [system+docs]
调用 2: [system(5K) + docs(50K) + question2] → 命中！只算 question2
```

50K 的文档只算一次，后面每次调用省掉 50K 的 prefill——这就是"砍掉 90%"的来源。

## 核心约束：前缀精确匹配

缓存的粒度是**前缀精确匹配**，这是全部策略的出发点：

- `[A+B+C]` 和 `[A+B+D]` → 只能复用 `A+B`，C 的计算省不掉；
- `[A+B]` 和 `[A+X+B]` → 第二次调用连 A 都复用不了（X 插在中间，前缀断了）。

推论很锋利：**prompt 的顺序就是性能，顺序就是钱**。

- ✅ 不变的部分放前面：system prompt → 静态文档 → 工具定义；
- ✅ 变化的部分放最后：用户问题、对话历史、多轮追加的内容；
- ❌ 在 system prompt 里塞时间戳、request_id、随机数——每次前缀都不同，缓存永远命中不了。

最后一条是生产环境最常见的死因：有人为了"可追踪"在 system prompt 头部加时间戳，结果缓存命中率常年 0%。**动态内容一律沉底，这是铁律。**

## 实战一：断点打在"稳定边界"上

Anthropic 的实现是显式标记：用 `cache_control` 打断点，最多 4 个。断点不是越多越好——每个断点都是一次"写缓存"的计费点。正确姿势是打在**稳定边界**上：

```
[system prompt 结束] ← 断点 1：几乎不变
[长文档/知识库结束] ← 断点 2：每天变一次
[工具定义结束]     ← 断点 3：发版才变
[用户问题...]      ← 不打断点：每次都变
```

断点的粒度决定了复用率：把"每天变一次"的文档和"每次都变"的问题切开，文档部分的缓存就能活一整天。反过来，如果你在"每小时变一次"的内容后面打断点，这个断点基本就是摆设。

还有一个细节：断点数量和"写缓存"次数成正比。3 个断点意味着每次调用写 3 段缓存——如果你的调用频率刚好卡在 break-even 边缘，减少断点、合并稳定内容，能直接把写入成本砍掉一半。**断点是按"变化频率"切，不按"逻辑模块"切**，这是新手最容易搞反的地方。

## 实战二：工具定义是第一优先级

MCP 普及后，一个被严重低估的 token 大户出现了：**工具定义**。接十几个 MCP server 时，工具 schema 轻松上万 token——每次调用都重新算一遍。

而工具定义恰恰是最适合缓存的内容：发版才变，前缀位置固定（一般紧跟 system prompt）。**先把工具定义的缓存命中率做到 95% 以上，再去优化别的**，这是投入产出比最高的一步。很多团队的缓存优化第一轮，做完这一步就停了——因为剩下的优化加起来，都不如这一步省得多。

## 实战三：长文档问答的算账

最适合 prompt caching 的场景：50K 字的文档 + 连续多轮提问。算一笔账（按 Anthropic 定价口径，命中 input 按 0.1x 计费，output 按 5x）：

```
无缓存，每轮：
  (55K input × 1.0 + 0.5K output × 5.0) = 57.5 单位

有缓存，首轮 57.5，之后每轮：
  (5K 新增 × 1.0 + 50K 命中 × 0.1 + 0.5K × 5.0) = 12.5 单位

10 轮总成本：无缓存 575 → 有缓存 57.5 + 9×12.5 = 170
```

**降了 70%，轮数越多降得越多**。问答轮数上 20 轮，成本直接除以 5。这就是"砍掉 90%"在真实场景里的样子——不是营销话术，是算术。

## 缓存命中的微观视角：KV Cache 到底是什么

为什么复用前缀能省掉 O(n²) 的计算？因为 Transformer 生成每个 token 时，都要 attend 之前所有的 token——这些"之前 token 的 key/value 表示"就是 KV Cache。Prefill 阶段算一遍存下来，decode 时直接读。

Prompt caching 的本质，是**把这份 KV Cache 从"一次性的中间变量"变成"可复用的资产"**，存到内存甚至硬盘里（DeepSeek 的硬盘缓存就是这么来的）。命中时，模型跳过 prefill 的矩阵乘法，直接从缓存加载——省的不只是钱，还有首 token 延迟（TTFT）：50K prompt 的 prefill 可能要几秒，命中缓存后几百毫秒就出首字。**缓存同时优化了成本和延迟**，这在优化手段里很少见。

但 KV Cache 和模型权重强绑定：模型一升级，缓存全失效。所以"模型版本"也是缓存 key 的一部分——**发版日记得看一眼缓存命中率，它会先跌为敬**。

## 三个坑

**坑一：写缓存也要钱。** Anthropic 写缓存收 1.25x，还有 5 分钟 TTL（可付费延长）。调用频率太低的话，写缓存的钱比省下来的多——缓存 5 分钟内只被用 1 次，纯亏。**Prompt caching 是高频场景的优化**，低频调用别折腾。算 break-even：命中带来的节省 > 写入成本 × 写入次数，不满足就关掉。

**坑二：缓存不是无限续杯。** TTL 到了，缓存就没了。默认 5 分钟——意味着两次调用间隔超过 5 分钟，下一轮重新全量计算。低峰期的定时任务、每天跑一次的批处理，基本吃不到缓存红利。设计调用节奏时把这一点算进去：**能凑成"burst"的流量，别摊成"细流"**。

**坑三：别在缓存前缀里放隐私。** 缓存的 KV 按组织隔离，不会串到别人家，这是底线。但同一组织内缓存是共享的——把用户隐私（姓名、订单号）塞进 system prompt 前缀，等于让它躺在共享缓存里。**复用边界 = 信任边界**，想清楚再放。

## 和 RAG、路由的组合拳

Prompt caching 不是孤立的优化，和另外两个手段是乘法关系：

- **RAG + 缓存**：检索出的文档拼进 prompt 后，在文档结尾打缓存断点。检索结果每天才变一次的话，文档缓存命中率轻松 95%+；
- **路由 + 缓存**：简单请求走小模型（便宜），复杂请求走大模型 + 缓存（思考贵但 prefill 省了）。两者叠加，总成本经常只有原来的 5%；
- **缓存 + 批处理**：把同一文档的多个问题攒成 batch 一次问，缓存写一次、读 N 次——写入成本被摊薄到可以忽略。

单独看，每个手段省 50%~90%；组合起来，**降本做到最后拼的不是单点优化，是组合**。

## 各家实现差异

| | Anthropic | OpenAI | DeepSeek |
|---|---|---|---|
| 触发方式 | 显式 `cache_control` 断点 | 自动（1024 token 起） | 自动 |
| 折扣 | 命中 0.1x | 有折扣，力度小 | 命中 0.1x，硬盘缓存 |
| TTL | 5 分钟（可延长） | 路由自动管理 | 较长 |
| 心智负担 | 要手动打断点 | 零 | 零 |

选型建议：用 Anthropic 就老老实实打断点，控制权在你手里，天花板最高；用 OpenAI/DeepSeek 就注意 prompt 顺序，剩下的交给自动缓存。**不管用哪家，"静态在前、动态在后"的顺序铁律都适用**——自动缓存也是按前缀匹配的，只是你不用手动标记而已。

## 什么时候别用缓存

缓存虽好，不是万能。有三种场景，开了等于白开甚至倒亏：

1. **低频调用**：每天几十次的内部工具，TTL 内根本凑不出第二次命中——写缓存的 1.25x 纯打水漂；
2. **prompt 高度动态**：每次请求 system prompt 都不一样（比如拼了用户画像），前缀永远对不上，缓存命中率天然 0%；
3. **强安全隔离场景**：多租户共用一个 API key，但租户间数据不能互见——缓存按组织隔离，可你的"组织"里有多个租户，复用边界就破了。这时候要么分 key，要么别缓存。

判断标准就一条：**同一前缀在 TTL 内会被复用 ≥3 次吗？** 达不到就别折腾，省下的钱还不够写缓存的。

## 真实案例复盘：一个客服系统的缓存改造

说个 composite 的真实案例（数字是多个项目的综合，不是某一家）：一个日均 2 万次会话的客服问答系统，system prompt 8K（含角色设定和 20 个工具定义），知识库文档 40K，平均每会话问 6 轮。

改造前：每轮全量 prefill 48K，月账单约 ¥21,000。改造动作只有三步：

1. 工具定义和 system prompt 打断点（一直不变）；
2. 知识库文档单独打断点（每天凌晨更新一次）；
3. 用户画像等动态内容沉底。

改造后：首轮全量，之后每轮只算新增问题 + 命中缓存的 48K（0.1x）。缓存命中率 93%，月账单降到 ¥4,800——**降了 77%，而代码改动不到 30 行**。

这个案例里最贵的一课不是技术，是顺序：他们第一版把"用户 ID + 时间戳"放在了 system prompt 开头，命中率 0%。挪到末尾，命中率直接 93%。**一行位置的改动，值 ¥16,000/月。**

## 上线检查清单

1. **审计 prompt 顺序**：静态内容在前、动态内容在后，时间戳/随机数一律沉底；
2. **断点打在稳定边界**：system 结尾、文档结尾、工具定义结尾；
3. **工具定义优先**：MCP 工具 schema 的缓存命中率先做到 95%+；
4. **盯住命中率**：Anthropic 返回 `cache_read_input_tokens`，低于 80% 就去查顺序；
5. **算 break-even**：低频场景先算账，写入成本大于节省就别开。

记住一句话：**prompt 的顺序就是钱，越稳定的放越前**。这可能是近年来所有 AI 工程优化里，投入产出比最高的一句。

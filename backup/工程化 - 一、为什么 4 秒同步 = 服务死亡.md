> 凌晨 3 点 PagerDuty 告警：CPU 30%、内存 60%，服务却死了。真凶是一个跑了 4 秒的同步循环。

先说结论：**在 Node 里，没有"很快"的同步代码，只有"数据量还不够大"的同步代码。** 测试环境的 1 万行数据跑 50ms，生产的 80 万行跑 4 秒——而这 4 秒里，这个 Node 进程什么都干不了。

```javascript
// 真凶：三个月前上线的"临时"报表导出
app.get('/api/export', (req, res) => {
  const rows = db.query('SELECT * FROM events'); // 80 万行
  const csv = rows.map(r => toCSV(r)).join('\n'); // 同步，跑了 4 秒
  res.send(csv);
});
```

# 一、为什么 4 秒同步 = 服务死亡

Node 是单线程事件循环，工作方式是：

```
┌──────────────────┐
│   同步代码执行     │ ← 你在这里卡 4 秒
├──────────────────┤
│   处理 I/O 回调    │ ← HTTP 请求、DB 返回，全在这里排队
├──────────────────┤
│   处理定时器       │
├──────────────────┤
│   setImmediate    │
└──────────────────┘
     ↑ 下一轮循环
```

**同步代码跑完，事件循环才能转下一圈。** 一个 200ms 的同步块，意味着这 200ms 内所有的网络响应、数据库回调、健康检查全部被延迟。这就是"Event Loop 饥饿"。

而雪崩是这么来的：4 秒内健康检查回不上 → K8s 判定 Pod 死亡 → 重启 → 流量打到其他 Pod → 其他 Pod 也开始导出报表 → 集体死亡。**一个同步循环，拖垮整个集群。**

# 二、两个更隐蔽的饿死方式

**process.nextTick 饥饿**：`nextTick` 的回调在"当前阶段结束前"全部执行完。如果你递归调用它，事件循环永远进不了下一轮：

```javascript
// 永远跑不完，事件循环被饿死——比同步循环更隐蔽
function foo() { process.nextTick(foo); }
```

同步循环至少"跑完就释放"，`nextTick` 递归是**无限期霸占**。很多"偶发卡死"的根因在这里。

**libuv 线程池的误解**：很多人以为"Node 的 I/O 都是异步线程做的"。错了一半——网络 I/O 是 epoll 真异步，但**文件 I/O、DNS、部分 crypto 走的是 libuv 线程池（默认 4 个线程）**。4 个大文件同时读，线程池占满，后面的文件操作照样排队。`UV_THREADPOOL_SIZE` 可以调，但治标不治本——**线程池是"有上限的异步"，不是"无限的异步"**。

# 三、排查：先量化，再定罪

**第一步，确认饥饿：event loop lag 探针。** 放到服务启动代码里常驻：

```javascript
setInterval(() => {
  const start = Date.now();
  setImmediate(() => {
    const lag = Date.now() - start; // 正常 < 10ms
    metrics.gauge('eventloop.lag', lag);
    if (lag > 50) logger.warn('Event Loop 饥饿！lag =', lag, 'ms');
  });
}, 1000);
```

**lag 持续大于 50ms = 饥饿实锤。** 我们的事故里，如果早有这个指标，第一次抖动时就能发现，而不是等到凌晨 3 点。把 lag 接进 Prometheus，比事后查日志有用 10 倍。

**第二步，定位真凶：火焰图。** 找"又宽又平"的同步块——正常的 I/O 等待是"窄"的（不占 CPU），同步计算是"宽"的。我们的真凶在火焰图里是一个 4 秒宽的 `JSON.stringify`，想认错都难。

```bash
npx clinic doctor -- node app.js   # 傻瓜式诊断
# 或原生：node --cpu-prof --cpu-prof-name=lag.cpuprofile app.js
```

**第三步，最小复现：灌生产级数据量。** 把可疑的同步操作单独拎出来，灌生产级别的数据量计时。测试环境的 1 万行和生产的 80 万行是两个世界。**能量化，才能定罪。**

# 四、三种修法：切片、worker、流式

```javascript
// 修完之后的样子：流式 + 每批让出
app.get('/api/export', async (req, res) => {
  res.setHeader('Content-Type', 'text/csv');
  for await (const batch of db.queryStream('SELECT * FROM events', { batch: 1000 })) {
    res.write(batch.map(toCSV).join('\n') + '\n');
    await new Promise(r => setImmediate(r)); // 每批让出一次事件循环
  }
  res.end();
});
```

内存从 2GB 降到 50MB，RT 从 4 秒降到首字节 100ms。三种修法的选型：

- **切片**：大循环拆 chunk，每 N 条 `await setImmediate` 让出。改动小，适合数据处理、批量任务；
- **worker_threads**：CPU 密集型扔给 worker 线程。适合加密、压缩、大 JSON 解析，但有进程间通信开销；
- **流式**：边读边处理，不全量进内存。改动最大，但最彻底，适合大文件、大结果集。

# 结语：防患清单

1. **监控**：`nodejs_eventloop_lag_seconds` 进 Prometheus，lag > 100ms 持续 1 分钟就告警；
2. **压测看 P99**：平均 RT 会掩盖饥饿，P99 不会。用生产级数据量压；
3. **CR 红线**：请求链路上的同步大循环、同步 crypto、大 JSON.parse/stringify，直接打回；
4. **混沌演练**：故意在预发环境放大同步块，看告警链路能不能在雪崩前 catch 住。

凌晨 3 点的教训很贵，但公式很便宜：**lag 指标确认 → 火焰图定位 → 切片/worker/流式修复**。以及永远记住——在 Node 里，同步代码的性能要用生产数据量来衡量，测试环境的数据量都是玩具。

# TypeScript 7.0：8-12 倍加速背后，是编译器架构的推倒重来

2026 年 7 月 8 日，TypeScript 7.0 GA（代号 Corsa）：编译器整体从 TS 移植到 Go，全量类型检查 8-12 倍加速，`strict` 默认开启。这是 TS 历史上最大的一次重构。但"用 Go 重写"这个描述掩盖了真正的故事：**Corsa 不是翻译，是重设计。**

# 一、旧编译器慢的根因：单线程 + 全量

tsc 的慢有两个结构性原因，和语言无关：

```
1. 单线程：V8 是单线程的，tsc 跑在 Node 里，天生只能用 1 个核
   → 16 核机器，15 个核在看戏

2. 粗粒度增量：改一个文件，tsc 要重查"可能受影响"的整个闭包
   → 100 万行项目，改 1 行，等 2 分钟
```

注意：这两点都是**架构选择**，不是"TS 语言慢"。V8 跑 JS 很快，慢的是"一次只用一个核 + 缓存粒度太粗"这套设计——而这套设计是 2012 年定的，那时还没有"百万行前端项目"这个概念。

# 二、Go 解决的是"并行"，不是"速度"

为什么选 Go 而不是 Rust？官方没明说，但从工程角度看，答案很直接：

```go
// 类型检查天然可并行：文件之间没有依赖时，各查各的
var wg sync.WaitGroup
for _, file := range program.Files {
    wg.Add(1)
    go func(f *File) {
        defer wg.Done()
        checkFile(f, sharedChecker)  // 只读共享状态，无锁
    }(file)
}
wg.Wait()
```

1. **goroutine 够轻**：类型检查是"大量小任务"（每个文件一个），goroutine 的调度开销比系统线程低两个数量级——Rust 的 rayon 也能做，但心智负担更高；
2. **AOT 无预热**：Go 编译成原生二进制，启动即全速。V8 跑 tsc 要先 JIT 预热，大项目上光预热就几十秒；
3. **团队现实**：TS 团队在微软内部，Go 工具链（VS Code 的 Go 插件、Azure 的 Go 服务）都是现成的——**选语言首先是选生态，其次才是选性能**。

8-12 倍的分解，大致是：**并行 3-4x × 更细的增量缓存 2-3x × Go 运行时 1.5x**。换语言只贡献了最后一项，前两项是重写时顺手把 14 年的技术债还了。

# 三、`strict` 默认开启：用性能换正确性

7.0 另一个大动作是 `strict` 默认开。老项目第一次跑 `tsc` 会爆出一堆错——**不是退化，是之前没查出来**。这两件事是绑定的：

```
旧世界：类型检查慢 → 开发者关掉 strict 提速 →  bug 漏过去
新世界：类型检查快（15 秒）→ strict 默认开也无感 →  bug 被拦下
```

**性能是正确性的前提。** 一个 2 分钟的检查，开发者会想方设法绕过它；一个 15 秒的检查，开发者愿意让它默认开启。Corsa 真正的野心不是"快"，是**让严格类型检查成为零成本的默认项**。

# 四、工具链的"编译型语言化"已经完成

把 TS 7.0 放进更大的图景：

```
打包：    esbuild（Go，2019）→ Rolldown（Rust，2026，Vite 8 默认）
转译：    SWC（Rust，2020）
类型检查： tsc Corsa（Go，2026）
Lint：    Oxc（Rust）
```

**JS 写的 JS 工具，正在被系统语言系统性取代。** 规律很清晰：凡是"计算密集 + 可并行"的工具链环节，最终都会迁到 Go/Rust——V8 的单线程天花板是硬约束，再优化也绕不过去。

# 结语

TS 7.0 的故事可以浓缩成一句话：

> **性能问题很少是语言问题，多是架构问题；但换语言常常是重构架构的唯一机会。**

没有人会批准"把 tsc 的架构推倒重来"这种项目，但"用 Go 重写"听起来像个新项目——同样的事，换个名字就通过了。Corsa 教给所有维护老系统的人一条路：**想还 14 年的技术债，先找一个无法拒绝的理由。**

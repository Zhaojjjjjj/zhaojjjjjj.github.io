# npm 幽灵依赖：删掉的包，为什么还能跑

周三下午，我 `npm uninstall` 掉了一个包，项目照常跑，测试全绿，我合了代码下班。周五生产环境重启了一台机器，服务起不来了——`Cannot find module`，指的正是我周三删掉的那个包。

删掉的包，本地能跑，生产却挂了。这就是"幽灵依赖"：**你的代码在用一个 package.json 里根本没声明的包**，而它之所以"能用"，全靠运气。

# 一、复现：删了包还能 require

```bash
$ npm uninstall lodash
$ node -e "console.log(require('lodash').VERSION)"
4.17.21
# 删了，还能 require 出来？
```

package.json 里已经没有 lodash，但 `node_modules/lodash` 还在——因为**别的包还在用它**。用 `npm ls` 能看到它的"鬼影"：

```bash
$ npm ls lodash
project@1.0.0
├── lodash@4.17.21 extraneous   ← 你的代码在用，但纸面上没人认领
└── other-lib@2.0.0
    └── lodash@4.17.21
```

`extraneous` 就是 npm 给幽灵依赖打的标记：**装着，但没人认领**。

# 二、根因：提升算法的三条规则

npm 3 之后 `node_modules` 默认**扁平化**。装 `other-lib` 时发现它依赖 lodash，先看顶层有没有——有就复用，不再装第二份。这叫"提升"（hoisting），目的是省磁盘、去重。

你执行 `npm uninstall lodash` 时，npm 删掉的是"你声明的那份依赖关系"，但发现 `other-lib` 还需要它，**于是把顶层的目录留下了**。你的代码 `require('lodash')` 照样解析到它——你从没声明，却一直在用。

提升的完整规则有三条，第三条是"CI 玄学"的根：

1. **顶层优先**：有满足版本要求的就复用，没有才装；
2. **版本冲突就嵌套**：顶层是 4.x，但某包要 `^3.0.0`，只能在它自己的 `node_modules` 下嵌套装；
3. **先到先得**：依赖树的遍历顺序决定谁先"占"顶层。

**安装顺序不同，顶层被谁占、谁被嵌套，结果就不同。** 本地是三年增量安装攒出来的顺序，CI 是干净安装的顺序——两棵树长得不一样，幽灵的藏身之处也不一样。周三本地全绿、周五生产爆炸，根子就在这里。

# 三、为什么这是颗雷：三种死法

**版本漂移**：顶层的 lodash 版本由 `other-lib` 的声明决定。它一升级，你的代码行为可能就变了，而你根本不知道你"依赖"过它。**你的构建结果，取决于别人的依赖树。**

**换包管理器原地爆炸**：pnpm 用硬链接 + 严格隔离，没声明的包直接 `MODULE_NOT_FOUND`。从 npm 切 pnpm 第一次安装必炸出一堆——**pnpm 是在帮你把雷提前引爆**。

**供应链盲区**：`npm audit` 只审声明的依赖树。幽灵依赖的版本变化（宿主包升级带进来一个有漏洞的 lodash），不会出现在审计视野里。**你不知道自己依赖的东西，就是你防不住的东西。**

# 四、根治：把"运行时玄学"变成"安装时错误"

四道防线，按见效排序：

**显式声明**：直接用的包必须写进 package.json，哪怕现在能从顶层解析到。铁律，没有例外。

**换 pnpm**：严格隔离让幽灵无所遁形。最大的功德是**把"运行时玄学"变成"安装时错误"**——错得早，总比错在生产好。

**CI 门禁**：`npx depcheck` 找出"用了没声明"和"声明了没用"的包，拦在合并前。配合 `npm ci` 干净安装（拒绝增量玄学），双保险。monorepo 里每个 workspace 单独跑一遍——workspace 之间的幽灵，症状一模一样。

**锁死版本**：`package-lock.json` 必须提交，CI 里永远用 `npm ci` 而不是 `npm install`。**安装命令不应该有副作用。**

# 结语

回到周三那个下午。如果删包之后跑一下 `npm ls lodash`，看到那个 `extraneous`，或者 CI 里有一道 depcheck 门禁，周五的那次重启就只是一次普通的重启。

> **幽灵依赖最可怕的从来不是"删了包还能跑"，而是"现在能跑，让你误以为永远能跑"。**

别让你的构建依赖运气：声明所有直接依赖，让 pnpm 和 CI 替你守夜。定期体检命令存好：`rm -rf node_modules && npm ci` 还原真实依赖树，`npm ls | grep extraneous` 让幽灵现形——**幽灵最怕的不是 depcheck，是"定期"。**

# 自适应推理：思考预算的决策权，交到了模型手里

同一个客服问答接口，上周平均每次调用烧 800 个 token，这周涨到了 9000——代码一行没改，prompt 一个字没动，账单翻了 11 倍。

查了一圈，根因不在我们这边：模型供应商把默认推理模式从"固定思考预算"切到了"自适应推理"。同一个问题，模型自己决定想多深。这就是过去一年最大的范式转移：**思考预算的决策权，从开发者手里，交到了模型自己手里**。

# 一、从"手动挡"到"自动挡"

自适应之前，思考预算是个超参，开发者手动指定：

```python
# 手动挡：你来决定想多深，不管难易都烧满 10000
response = client.messages.create(
    model="claude-4",
    thinking={"type": "enabled", "budget_tokens": 10000},
)
```

简单问题（"翻译这句话"）和困难问题（"证明这个定理"）烧同样的预算——前者浪费钱，后者可能还不够。自适应之后调用签名没变，内部变了：简单问题 ~0 token 直接答，数学证明 ~20K token。看起来只是少了一个参数，**但问题是：模型凭什么知道一个问题有多难？**

# 二、难度估计的三档实现

核心是一个**难度估计**环节，业界三种实现：

**轻量分类器前置**：小模型跑在主模型之前，看一眼 query 打难度分，按档位分配 budget。便宜、快速、可解释——但它只看"问题长什么样"，不看"对当前模型有多难"。

**小模型试水**：先用便宜的小模型答一遍，看 confidence 和自洽性。一次答对且确定→简单；反复横跳→难，值得深想。**用廉价试错代替难度预判**，Agent 场景常见。

**边想边评估（early stopping）**：不预判，直接开想，思考中持续评估"还要不要继续"。最"自适应"，但工程最复杂——"想够了"的停机条件本身又是个超参。

# 三、"难"的行为主义定义

不管哪一档，都要回答：**什么叫"难"？** 直觉答案"人类觉得难"是错的——对模型的"难"和对人类的"难"经常是反的。人类觉得难的哲学思辨，模型零思考张口就来；人类觉得简单的"数图里有几个 R"，模型可能烧几千 token 还数错。

正确做法是**行为主义**的：不问人觉得难不难，只问"多给思考预算，答案质量提升多少"：

```
对验证集每个问题：budget=1K 得分 S1，budget=10K 得分 S10
难度 = S10 - S1   # 边际收益越大，越"难"
```

这个定义漂亮在它是**模型相关**的：同一个问题，对强模型"简单"，对弱模型"困难"，预算自动跟着能力走。代价是标注成本——每个问题跑两遍大模型，而且难度**分布外脆弱**：没见过的问题类型，分类器只能瞎猜。这就是自适应上线初期总有一批"看起来简单、实际烧爆"的问题。

# 四、误判的两种死法，不对称

| 误判方向 | 症状 | 代价 |
|---|---|---|
| 欠思考（难题当简单） | 答案错，又快又便宜 | **质量事故**：错误答案比慢更贵 |
| 过思考（简单题当难题） | 答案对，烧 10 倍 token | **成本事故**：账单涨，延迟涨 |

注意过思考的延迟代价：20K token 按 50 token/s 就是 400 秒。用户问"今天星期几"，等 6 分钟拿到正确答案——**这比答错更侮辱人**。

所以工程化的第一件事不是调分类器，而是**给两种死法分别设防线**：

```python
response = client.chat.completions.create(
    model="gpt-5.1",
    reasoning_effort="adaptive",
    max_reasoning_tokens=8000,  # 防线：再自适应也不能超过这个数
)
```

**自适应不等于无上限。** 以前 budget 写在代码里看得见，现在藏在模型肚子里——看不见的预算最容易失控。

# 五、被低估的第三种成本：延迟方差

思考 token 顺序生成，20K token 就是 400 秒干等——这 400 秒里，你的并发连接还被占着。自适应有个隐蔽的系统性代价：**思考深度的方差，直接变成延迟的方差，进而变成容量规划的噩梦**。

```
固定 budget 10K：P99 延迟 ≈ 200 秒，可预测，可做超时降级
自适应 0~30K：  P50 延迟 5 秒，P99 延迟 600 秒
```

P99 涨 3 倍，同样 QPS 要准备 3 倍连接池。**省下来的 token 钱，可能以服务器成本吐回去。** 这就是很多实时场景（客服、语音）退回"规则分级 + 固定 budget"的原因：不是自适应不准，是延迟方差扛不住。

# 结语

自适应推理的真正含义，不是"不用管思考预算了"，而是：

> **思考预算从"静态配置"变成了"动态观测对象"。**

决策权交给模型的那天起，你的工作就从"调参"变成了"审计模型调的参"。落地四件事按顺序做：建 `reasoning_tokens` 分布基线（没有分布图，对成本的感知就是玄学）；按任务类型设不同上限（上限本身就是先验知识）；AB 测试自适应 vs 规则分级（70% 场景下后者更便宜）；把成本归因到业务指标（"解决一个工单多少钱"，而不是"token 花了多少"）。自动挡的车，依然需要仪表盘。
